# Networking

Your server needs to be reachable by your own devices. On your home network that works straight away. From outside, something has to let traffic in, and the server tries to arrange that by itself.

## The port

The server listens on port **7626**, and uses the same number on the outside by default. You can change either with the `--internal-port` and `--external-port` options.

It also opens **7627** for its own health checks. That one is loopback only, so nothing outside the machine can reach it, and it never needs a rule.

## How the server gets itself reachable

Setup does this without asking you anything. In order, it tries to:

1. **Open a port on your router.** The server asks the router directly, using UPnP, and then asks the NoMercy API to connect to that address from the internet. A router that accepts the request but does not actually forward anything is common, which is why the check runs from outside instead of trusting the reply.
2. **Use the tunnel assigned to your server.** When the port is not reachable from outside and your server has a named tunnel, traffic goes through that tunnel. It works even when your router allows nothing inbound. A NoMercy subscription assigns a named tunnel to each of your servers on its own, and a server that is running on a quick tunnel moves to it within a minute.
3. **Open a quick tunnel.** When there is no verified port and no named tunnel, the server opens a free Cloudflare quick tunnel on its own. It needs no account, no token and no router change. Cloudflare hands out a random `trycloudflare.com` address for this run, and your apps get that address from NoMercy the moment it is live. The address changes every time the server starts; your apps follow it without you doing anything.

A port forward that answers from outside always wins, even when a tunnel is assigned to the server. The tunnels are the fallback, not the default. Every server ends up reachable from outside on one of the three, whatever the router allows.

When even the quick tunnel cannot connect out, the server stays reachable on your own network only, and keeps retrying in the background with growing gaps between attempts.

## Adding the rule yourself

Some routers have UPnP switched off, and some ignore the request without saying so. If your server works at home but not away from home, add the rule by hand in your router's admin page.

Forward external port **7626** to internal port **7626** on the machine running the server, for **both TCP and UDP**.

Both, because the server speaks HTTP/1.1 over TCP and HTTP/3 over UDP. The automatic mapping the server makes for itself creates both, so a hand-written rule should match it.

A TCP-only rule still connects. Clients that could have used HTTP/3 fall back to the slower route.

Give the server machine a fixed address on your network while you are in there. Your rule points at one address, and a router is free to hand that address to a different device later.

::Troubleshooting

**It works at home, not away from home.**
Nothing established an outside route. Add the port rule above.

**It stopped working after a router restart or a power cut, and I added the rule by hand.**
The router most likely gave the server machine a different local address, so your rule now points somewhere else. Give that machine a fixed address and update the rule. The server notices address changes and re-establishes its own route; a rule you wrote by hand is the part that cannot follow.

**Nothing reaches the server at all, even at home.**
Check the machine's firewall. On Windows the prompt appears the first time the server runs and has to be allowed.

::
