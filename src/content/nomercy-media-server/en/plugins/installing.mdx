# Installing and Managing Plugins

Everything here lives on one screen, under Dashboard > Plugins. It is owner-only on every
client, because approving what a plugin may do is the server owner's decision and nobody
else's.

## Two ways in

You can hand the server a file, or point it at a repository and pick from what that
repository offers. Both end in the same place: the plugin is on disk, disabled, waiting for
you to look at what it asked for.

**A file you already have.** Press Install on the plugins page and pick the plugin's `.dll`.
The upload is staged outside the plugins folder and only moves in once it passes
verification, so a file the server rejects is never left somewhere it would be found on the
next start.

**A repository.** Open the catalog, add a repository by name and index URL, then install
from the list. The server resolves the download against its own copy of that index, so the
browser never names a URL. If the repository published a checksum it is checked before
anything is copied into place, and if it did not, the prompt says so before you agree.

Publishing your own index is one JSON file. See
[Publishing a Plugin Repository](/nomercy-media-server/plugins/repository-index).

## Approving what a plugin asked for

A plugin declares what it needs before it runs: outbound hosts, hooks, whether it serves
REST or a socket, and which screens it contributes. Anything past the baseline installs
disabled and cannot start itself.

The plugin's page shows that declaration in full, hosts included, rather than the word
"network". One line to read carefully is whether any of its endpoints answer a caller with
no token: every plugin route asks for one on the server's own terms unless the manifest says
otherwise, so that line is the whole answer and the plugin's own code cannot overrule it.

Approving is one action that records your consent, records the grants that came with it, and
starts the plugin. Your consent covers the set you were shown. An update that asks for more
than that loads disabled and comes back to this page with the addition named, so a plugin
cannot grow its reach through an update you installed without reading.

Withdrawing takes all of that back and stops the plugin, and you can approve again later.

Where the plugin came from does not stand in for any of this. A repository you marked
trusted still ships plugins that ask you before they run.

Some plugins ask for something afterwards that their manifest could not know up front, such
as a host they only learn about at runtime. Those requests sit at the top of the plugins
page until you allow or deny them, because a plugin waiting on you is a plugin not doing its
job.

## Turning one off

Disable stops the plugin and leaves it installed with its configuration intact. Use it to
find out whether a plugin is behind something you are seeing.

Some changes need the server restarted before they take effect. The plugin's row says so
when that is the case, and says why. When it says nothing, the change is already live.

## Removing one

Uninstall removes the plugin and its files from the server. What it stored is a separate
question and the dashboard asks it: keep the plugin's data, or take it too. Taking it removes
the data folder along with your consent, the grants that came with it and any secrets the
plugin held, and none of that is recovered. Keeping it means reinstalling the same plugin
later finds its settings and its library where it left them.

## Updates

The catalog compares what each repository offers against what is installed, and puts
anything newer at the top of its own page. The comparison happens on the server, so every
client agrees about whether an update exists.

Updating is the same operation as installing, against a newer version.

## When a plugin fails to load

A plugin that broke on startup is listed apart from the ones you turned off. It is not off,
because nobody chose this, and enabling it again fails the same way until the cause is
fixed. The server log says what went wrong.

## Configuring one

A plugin's settings live inside the plugin, on the screens it registered. Those appear on
its page and in the sidebar once it is enabled, and the server hands each screen back to the
plugin to draw.

## When a build is withdrawn

The server checks a list of withdrawn builds before it runs a plugin. A build on that list
stops, and the plugin's row says why. The list names one build, not the plugin, so the
publisher's next release installs normally and you do not have to wait for anything to be
lifted.

The server keeps the list on disk, so it still knows what it was last told after a restart
with no connection.

## When the server cannot reach NoMercy

If the server has not been able to refresh that list for more than seven days, it pauses
every plugin, free ones included. It does this because after a week it can no longer honestly
say none of them was withdrawn, and answering yes to a question it cannot check is the thing
this is here to prevent.

Nothing is uninstalled and nothing you approved is lost. The plugins start again on the next
successful check.

A list that does not carry a valid NoMercy signature is discarded and the one already on the
server is kept, so nobody who can answer for that address can pause your server or tell it a
withdrawn build is fine.

## Paid plugins

A paid plugin runs while the account that owns this server holds an entitlement for it. The
server keeps what it was last told in a signed bundle on disk, so it knows what you own
after a restart with no connection.

If the server cannot refresh that bundle for more than seven days, a paid plugin goes
dormant: installed, listed, not running. Nothing is deleted while it is dormant, and it
starts again on the next successful refresh. Someone whose internet is down has not stopped
paying.

An owner who never bought a plugin is told to buy it rather than told about the clock, and
an owner who did is told about the clock rather than sent to a shop they already used.

A bundle that does not carry a valid NoMercy signature is discarded and the one already on
the server is kept. That applies the same way to a bundle NoMercy pushes as to one the
server fetched.

## A server with no internet

A server that will never reach NoMercy can still run plugins. Turn on offline mode, then
import a bundle you downloaded from nomercy.tv on a device that is online. The bundle
carries the same two answers a connected server fetches: what this server owns, and which
builds were withdrawn.

Importing is all or nothing. A bundle that is not signed by NoMercy, was edited after it was
signed, or is older than the validity it was issued with changes nothing on the server, and
the message says which of those it was.

A bundle carries its own validity and that number is the one that counts, so a bundle issued
for sixty days is good for sixty days whatever this server is set to. Import a new one before
the old one runs out and nothing pauses.
