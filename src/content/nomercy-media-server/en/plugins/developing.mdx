# Writing a plugin

A plugin is a .NET assembly the server loads at runtime. This page covers the shape of one; the interfaces themselves are documented in the contract package.

## Starting from the template

The repository ships a project template under `templates/NoMercy.Plugin.Template`, which is the fastest correct start.

There are sample plugins under `tests/` as well, including a minimal one, one that adds dashboard UI, and ones that fail deliberately so you can see how the server reacts.

## The shape of a plugin

Implement `IPlugin`. It gives the server a name, a description, an id and a version, and receives an `IPluginContext` when it initializes.

Then implement whichever extension points you need:

| Interface | For |
|-----------|-----|
| `IMediaSourcePlugin` | Finding media the server would not find |
| `IMetadataPlugin` | Supplying titles, artwork and details |
| `IEncoderPlugin` | Overriding the encoding profile for a title |
| `IScheduledTaskPlugin` | Work on a cron schedule |
| `IAuthPlugin` | Taking part in authentication |
| `IUiPlugin` | Adding navigation and screens |

`IPluginServiceRegistrator` and `IPluginConfiguration` are available when you need dependency injection or your own settings.

## Building a user interface

`IUiPlugin` describes screens rather than rendering them. You return a description of the view and each client draws it in its own idiom: web, phone and TV.

Write the screen once and it looks native everywhere, which is the reason for the indirection.

## Declaring capabilities

Your manifest declares what the plugin needs: hooks it implements, network hosts it will reach, where it mounts UI, and whether it serves endpoints or sockets.

Declare the narrowest set that works. A plugin needing only media source, metadata or UI is installed and enabled straight away. Anything asking for network access or its own endpoints waits for the server owner to consent, which is friction you inflict on every one of your users.

Network access is limited to the hosts you declared. Reaching elsewhere fails unless the owner grants that host.

The set you declare is the set the owner approved. A manifest can ask for more than that: a hook it did not carry before, `rest` or `ws` switched on, or another network host. Any of those loads disabled until the owner approves the wider set. Ship the capabilities you need from the first release rather than growing into them.

## Endpoints that ask for a token

Every route your plugin serves carries the server's own authorization, imposed by the host in the same pass that puts your controller under `api/v{version}/plugins/{pluginId}`. An `[AllowAnonymous]` written in plugin code is taken back off, because which endpoints are open is the owner's decision and not yours.

An endpoint that answers a caller with no token is one line in the manifest:

```json
{
  "capabilities": {
    "rest": true,
    "restAnonymous": true
  }
}
```

`restAnonymous` is off unless the manifest says otherwise, and it applies to every route the plugin serves. The owner reads it beside the rest of your declaration before consenting, which is the point of putting it there.

Ask for it only when the caller genuinely cannot hold a token, such as a webhook another service posts to, and say why in your description.

## Asking at runtime

When you cannot know something in advance, such as a host the user configures themselves, ask for it while running through `IPluginGrants.RequestAsync`. Give a real reason: the owner sees it and decides on it.

## Packaging

Ship a `.zip` containing your manifest and assembly, or a bare `.dll` for something trivial.

To publish through a repository, list it in a catalog with a download address and a checksum. A published checksum describes one file, the `.zip` as you uploaded it.

A checksum published against anything else is refused, with the file it saw, the file it wanted, and how to republish. Release as a `.zip` and hash that file. See [Publishing a Plugin Repository](/nomercy-media-server/plugins/repository-index).

## Compatibility

The server checks that your plugin targets a compatible version before loading it. A plugin built against a different version is rejected outright rather than loaded and left half-working.

Rebuild against the contract package when the server has a major update.
