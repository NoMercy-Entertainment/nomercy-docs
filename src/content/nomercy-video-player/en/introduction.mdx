# What is nomercy-video-player

`nomercy-video-player` is a headless HTML5 video player: HLS streaming (native on Safari, `hls.js` everywhere else), VTT and ASS/SSA subtitle rendering, chapters, quality switching, and a plugin system, all driven by events and methods you call yourself. It ships no player chrome, no play button, no scrubber, no volume slider baked into the bundle, only a `<video>` element and a typed surface to drive it. Everything visible on screen is code you write, or a plugin you add.

It is built on [`nomercy-player-core`](/nomercy-player-core/introduction), the kit that also powers `nomercy-music-player`. The kit supplies the lifecycle, queue, plugin runtime, i18n, and auth; `nomercy-video-player` adds the one piece the kit cannot: an `HTMLVideoElement` backend and every method specific to watching video instead of listening to audio, fullscreen, picture-in-picture, theater mode, aspect ratio, subtitle and audio track selection, quality levels.

## Who it's for

Reach for `nomercy-video-player` when you're building a video-watching experience: a streaming app, a media dashboard, a player embedded inside a bigger product, and you want the UI to be genuinely yours instead of skinning someone else's chrome with CSS overrides. If you're composing a third kind of player entirely, not video, not music, start one level down at [`nomercy-player-core`](/nomercy-player-core/introduction) instead.

## Why it exists

Video has one job that's genuinely hard: playing an adaptive stream reliably across browsers while keeping subtitles, chapters, and quality switching in sync with it. `nomercy-video-player` owns that job through a swappable video backend. The shipped `Html5VideoBackend` passes HLS through natively on Safari and falls back to `hls.js` everywhere else, so you write `player.play()` once and never branch on browser. Everything that isn't video-specific (queueing, transport, volume, auth, plugins) comes from `nomercy-player-core` instead of being reimplemented here, so a fix that lands in the kit reaches the music player too.

## The setup, then freedom, model

The convention will be familiar from JWPlayer or video.js: create a player instance bound to a container, call `setup(config)` once with a strict, typed shape, wait for it to resolve, then do whatever you want. `nmplayer(id)` is the factory, the same role `jwplayer(id)` and `videojs(id)` play in those libraries. It returns the existing instance for an id already in use, or mounts a fresh one into the `<div>` at that id.

```ts
import nmplayer from '@nomercy-entertainment/nomercy-video-player';

const player = nmplayer('player-container').setup({ /* ... */ });
await player.ready();
```

`setup()` is the only strict part. It walks the same fixed pipeline every kit-composed player runs (config snapshot, plugin registration, stream, auth, playlist, and media readiness) before `ready()` resolves; call it twice and it throws instead of leaving the instance half-configured. Once `ready()` resolves, there is no prescribed UI at all. Build your own controls against the typed method surface, or add `DesktopUiPlugin` for a full prebuilt overlay you can still restyle. Both paths call the same `play()`, `pause()`, `subtitle()`, and `quality()` methods underneath.

## What you get

- **`NMVideoPlayer<T>`**, created through the `nmplayer(id)` factory, generic over your own playlist item type.
- **HLS playback** through a swappable video backend: native pass-through on Safari, `hls.js` everywhere else, plus quality levels and bandwidth introspection for ABR.
- **Subtitle rendering**: VTT out of the box, ASS/SSA with embedded fonts through `OctopusPlugin`, and a `subtitleStyle()` surface for user-customizable rendering.
- **Chapters and segment windows** (`chapters()`, `playSegment()`) for intros, recaps, and credits.
- **Fullscreen, picture-in-picture, theater mode, and aspect ratio** as first-class state, not DOM you maintain by hand.
- **A plugin system**: `KeyHandlerPlugin`, `OctopusPlugin`, and `V1VideoCompatPlugin` ship from the main package; a desktop overlay UI, cast, DRM, live transcoding, and TV remote handling ship as further opt-in plugins instead of bundle weight everyone pays for.
- **Everything from `nomercy-player-core`** underneath: lifecycle, queue, transport, volume, i18n, and auth-aware fetch, so it never gets reimplemented per medium.
