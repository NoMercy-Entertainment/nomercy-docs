# How It Works

`setup()` hands your config to the player core, which runs [nine stages](/nomercy-player-core/tour/lifecycle) before `ready()` resolves.

This page is the video layer wrapped around that sequence.
It decides which item loads first, what fills the container while it loads, and which tracks are playing by the time a frame appears.

## What setup fills in

Your config object is enriched before the core ever sees it.

| Field | What the video player puts there |
| --- | --- |
| `crossfadeEnabled` | `false` |
| `preloadLeadSeconds` | `10` |
| `preloadStrategy` | `VideoPreloadStrategy`, built with that lead |
| `transitionStrategy` | `GaplessTransitionStrategy` |

Each one is filled in only when your own config left it out.
A value you pass always wins.

`VideoPreloadStrategy` is the video-shaped list of what to prefetch for the next item: its media URL, poster, preview sprite, subtitle sidecars, chapter file and fonts.

One field is applied on the way out of `setup()` rather than during the sequence.
`theaterDefault` calls `theater(true)` before `setup()` returns, so the layout is already in theater mode while the stages are still running.

Everything else on this page happens after that.

## The player loads the first item itself

`setup()` arms the queue. It loads nothing.

The load is a separate pass, and it runs whether or not `autoPlay` is set.
That is what keeps a player from mounting blank.

A queue still empty at that point primes nothing.

**Calling `item()` yourself between `setup()` and `ready()` keeps your choice.**
The pass sees an explicit navigation and loads that item, with no resume applied.

{/* partial */}
```ts
player.setup({ baseUrl, playlist });

// Your pick, not the resume rule's.
player.item(2);

await player.ready();
```

## How the first item is picked

With no pick of your own, the choice comes from the `progress` field on your items.

Items carrying no `progress` at all leave the choice at the first item in the list.

Otherwise the item with the newest `progress.timestamp` wins, and its `percentage` decides what happens to it.

Past 90, the player rolls forward to the next item in the list and starts it from the beginning.
The last item has nowhere to roll forward to, so it starts over instead.

Below 90, the player loads that item and starts at its `progress.time`.

That offset rides the load down to the backend rather than being seeked afterwards, so the stream begins at the offset instead of fetching the opening first.

## The backend arrives with the first load

The video backend is built on that first load, not during setup.
That is the moment `muted` and `controls` from your config reach the element.

`html5` is the only kind with a built-in implementation.
Any other kind needs a `backendFactory` in your config, covered in [the video backend adapter](/nomercy-video-player/plugins-adapters/adapter-video-backend).

## What the container shows while it loads

The item's image goes onto the video element as its poster before the source is attached.
That is what fills the container until there is a frame to show.

An image already written as an absolute URL is used as given.
A relative one is joined to `baseImageUrl` in the same tick, then upgraded if your own `urlResolver` returns something different.

## Track selection settles on mediaReady

The load path emits `mediaReady` again once the backend really holds the item.
That second one is the video player's cue to choose tracks.

A `videoRect` event carrying the displayed picture rectangle is emitted inside that same dispatch, so your own `mediaReady` listener runs after it rather than before.

Selection is by language tag, never by track index.
`defaultAudioLanguage` and `defaultSubtitleLanguage` are matched exactly first and then by prefix, so `en` matches `en-US`.
A tag matching nothing leaves an unselected slot alone.
Where a track is already selected it does not: the slot is handed to the stream's own default rendition instead, with no warning.

A language the viewer already chose on an earlier item wins over the config default.

`defaultQuality` is applied on the first `levels` event and only then.
A quality chosen after that survives the next item, because the config value is never reapplied.

## The first frame

The backend's `canplay` is the point the player treats as the first frame.

`firstFrame` is emitted there.

The phase only moves to `playing` if something called `play()`, so on the default path it stays at `ready` and no `phase` event fires.

It fires once per source. Loading another item resets the latch, so the next item announces its own.

```ts
player.on('firstFrame', () => {
  hideYourOwnPlaceholder();
});
```
