# State and Events

Nothing here needs polling.

The player announces a value when it changes, and holds the same value for you to read back on demand.
`player.on('levels', handler)` reacts to a change, and `player.qualityLevels()` answers right now.

Both come from one place, so a menu built on the event and a menu built on the reader never disagree.

## What it announces

The names fall into six groups.

- Playback signals, including the first painted frame and the buffering stalls.
- Quality levels, once the manifest has been parsed.
- Subtitle cues, one channel whatever the cue came from.
- Display state: fullscreen, picture-in-picture, theater, aspect ratio, and the video rectangle.
- Segment boundaries, when you asked the player to watch a window.
- On-screen messages and navigation intents.

[Reference: Events](/nomercy-video-player/reference/events) carries every name, its payload and what makes it fire.

**The last group is not the player talking.**
Those events are raised by the interface and key-handling plugins, so a build that registers neither never sees one.
They are on the map because your own code listens for them, not because the player produces them.

## The rectangle the picture actually fills

`videoRect()` is the one reader with no equivalent anywhere else in the kit.

It returns the box the picture occupies inside your container, which is smaller than the container whenever there are black bars.
An overlay aligned to the container sits over the bars.
An overlay aligned to this rectangle sits over the picture.

It answers `null` until the video has metadata.
The `videoRect` event fires whenever the box moves: on `mediaReady`, on `duration`, on `fullscreen`, and on a resize of either the container or the video element.
The `mediaReady` one is emitted inside that dispatch, so a `mediaReady` listener of your own runs after it.

## See it running

Play, pause and seek in the native bar.
`playState()` and `time()` follow each move without a poll.

## The failures you have to answer

Most failures arrive on the four severity channels, and [Errors](/nomercy-player-core/tour/errors) is where those live.

Two refusals are yours to answer here, because in both the browser overrules the player.

### Autoplay

A browser declines to start playback that no one asked for.
That is the ordinary outcome of `autoPlay: true` on a page the viewer has not touched yet.

The player does not pretend otherwise.
It rolls `playState()` back to paused, rolls the phase back to where it started, emits `playPrevented`, and rethrows.

Without the rollback, every control drawn from state would show a pause button over a silent picture, and the viewer's first click would pause something that never played.

```ts
player.on('playPrevented', ({ reason, cause }) => {
  if (reason === 'backend-refused') showTapToPlay(cause);
});
```

`key reason` is one of four, and only one of them is the browser.

| `key reason` | Raised when |
| --- | --- |
| `str backend-refused` | The browser rejected the play call. |
| `str listener-prevented` | One of your own `beforePlay` listeners called `preventDefault()`. |
| `str delay-rejected` | A promise a `beforePlay` listener passed to `delay()` rejected. |
| `str delay-timeout` | Those promises took longer than `key beforeEventTimeoutMs`, ten seconds by default. |

The first is the only one that also throws.
A `play()` you await therefore rejects, and a `play()` you do not await becomes an unhandled rejection.

```ts
try {
  await player.play();
}
catch {
  // Already reported through playPrevented.
}
```

**The autoplay attempt `setup` makes for you is different.**
The player starts that one itself and handles its own rejection, so nothing reaches your console.
`playPrevented` is the only notice you get.

Muted playback is the case browsers do allow, so `muted: true` beside `autoPlay: true` is what makes the attempt succeed.

### Fullscreen and picture-in-picture

Both need a user gesture, and both are requests rather than commands.

`player.fullscreen(true)` emits `fullscreen` with the state it asked for, whether or not the browser agreed.

`player.fullscreen()` answers `str on` while the browser is in fullscreen, and also `str on` for the last request the player made.
Nothing withdraws that request, so a refused call and a viewer pressing escape both leave it reading `str on` while the browser is out.

`player.platform().fullscreen.isActive()` answers for the browser alone, and it is the one a button icon should follow.
`pip()` has the same shape.

Calling either on a player set up without a platform controller throws instead: `str core:policy/fullscreenUnsupported` and `str core:policy/pipUnsupported`.
The default platform supplies both, so this is a wiring mistake rather than a runtime condition.
