# Transport

The video player overrides none of the core's transport methods.

`play()`, `pause()`, `stop()`, `togglePlayback()`, `next()`, `previous()`, `rewind()`, `forward()` and `restart()` are [the core transport contract](/nomercy-player-core/tour/transport), and they behave here as that page describes.
`time()` is a core method too, and the page that describes it is [Time](/nomercy-player-core/tour/time).

What video adds underneath them is a real `<video>` element, and an element that answers back.

## The element answers back

The player drives the element and also listens to it.
Where the two disagree, what the element reports wins.

| The element fires | The player does |
| --- | --- |
| `play` | Sets the play state to playing and emits `play`, unless it already read as playing. |
| `pause` | Sets the play state to paused and emits `pause`, unless the element has already ended. |
| `loadstart`, `emptied` | Emits `pause` when the play state was playing. A new source is not a continuation. |
| `timeupdate` | Emits `time`, carrying the element's own position. |

The element's `playing` event passes through as `playing`, with no state change attached to it.

This channel exists because the element changes state without being asked.
The end of the file and a source swap during `load()` both pause it.
A stall does not: it raises `waiting` and `stalled` while playback stays where it was.

Without the sync the play state would still read `str playing` afterwards.
`togglePlayback()` would then call `pause()` on something already paused, and the viewer's next click would do nothing.

Two guards keep the channel quiet:

- The `pause` a browser fires immediately before `ended` is suppressed, so a film that runs to the end reports `ended` rather than a pause first.
- A `play()` you called yourself is not announced twice, because the bridge only emits when the play state was not already playing.

## Position comes from the element

`time()` with no argument returns the position the last `timeupdate` published, read off the element itself.

`stop()` pauses the element and returns it to `0`.

`duration()` is `0` until the element has metadata.
The player fills it from the element's `loadedmetadata` event, and resets it to `0` on every item change.

**`seekByPercentage()` does nothing while duration is `0`.**
A scrubber wired to it is inert until metadata lands, which is the usual reason an early click looks ignored.

Between a `next()` and the incoming item mounting, the outgoing element is still attached and still ticking.
The player suppresses `time` for that window, so a watch position is never written against the wrong item.

## When the browser refuses to play

`play()` forwards to the video element's own `play()`, and a browser declining playback without a gesture rejects there.

The player treats that rejection as a refusal rather than a success:

- The play state rolls back to `str paused`.
- A `str starting` phase rolls back to `str ready` or `str paused`.
- `playPrevented` fires with reason `str backend-refused`, carrying the browser's own error as `key cause`.
- The rejection is rethrown.

**An unawaited `play()` therefore becomes an unhandled rejection in the console.**

```ts
player.on('playPrevented', ({ reason }) => {
  if (reason === 'backend-refused')
    showTapToPlay();
});

try {
  await player.play();
}
catch {
  // Already reported through playPrevented.
}
```

`muted: true` is what makes the refusal unlikely.
A muted element is the case browsers allow with no gesture, and the player mutes the element from that config before any `play()` call reaches it.

The playback the player starts for you is already caught.
`autoPlay: true` and every `item()` navigation swallow their own rejection, so a refusal on those paths reaches you as `playPrevented` and nothing more.

The call you write yourself is the one you have to catch.

## Playing one stretch

`playSegment({ startSec, endSec, onEnd })` is the one transport-shaped call video adds.

It seeks to `key startSec`, watches each `time` event for `key endSec`, and emits `segmentBoundary` when the boundary is crossed.

[Reference: Video Player Methods](/nomercy-video-player/reference/player-methods) carries it, together with `clearSegment()` and the three `key onEnd` behaviors.

## See it running

`controls: true` sets `controls` on the video element and nothing else.

**Its buttons drive the element, never `play()` or `pause()`.**
The element reports back through the channel above, so `playState()` and `time()` stay correct.
What the bar skips is the dispatch, so no `beforePlay` or `beforePause` listener sees a native click.
