# Plugin Development: Video Player

Plugins for `nomercy-video-player` are core plugins. The whole shared toolkit lives on the `Plugin` base: `mount`, `createElement`, `createButton`, `addClasses`, `listen`, `timeout`, `frame`, `fetch`, `t`, `emit`, and the rest of `this.*`. The [Plugin Handbook](/nomercy-player-core/handbook/anatomy) teaches every one:

- [Anatomy of a Plugin](/nomercy-player-core/handbook/anatomy), the class shape, generics, and lifecycle
- [Building DOM](/nomercy-player-core/handbook/building-dom) and [Styling](/nomercy-player-core/handbook/styling)
- [Listening](/nomercy-player-core/handbook/listening) and [Timing](/nomercy-player-core/handbook/timing)
- [Emitting](/nomercy-player-core/handbook/emitting), [Network](/nomercy-player-core/handbook/network), [i18n](/nomercy-player-core/handbook/i18n)
- [Errors & State](/nomercy-player-core/handbook/errors-state) and [Registration](/nomercy-player-core/handbook/registration)

This page teaches only what a video plugin can reach that a bare core plugin cannot. That is the video element, the track surfaces, chapters, the display states, and the overlay stack over the video.

## Built-in plugin catalog

All built-in plugins are importable from `@nomercy-entertainment/nomercy-video-player/plugins`.

| Plugin | Plugin id | What it does |
| ------ | --------- | ------------ |

## Typing against the video player

Use `IVideoPlayer` as the `P` generic. It is the stable public interface for the video player and the correct type for plugins and consumer functions. `NMVideoPlayer` is the concrete class, an implementation detail; a plugin typed against it depends on the class hierarchy for no gain.

```ts
import { Plugin } from '@nomercy-entertainment/nomercy-player-core';
import type { IVideoPlayer, VideoPlaylistItem } from '@nomercy-entertainment/nomercy-video-player';

export class MyVideoPlugin extends Plugin<IVideoPlayer<VideoPlaylistItem>> {
	static override readonly id = 'my-video-plugin';
	static override readonly version = '1.0.0';

	override use(): void {
		this.on('item', ({ item }) => {
			// item is a VideoPlaylistItem
		});
	}
}
```

`IVideoPlayer<T>` takes your playlist item type as its generic. Extend `VideoPlaylistItem` with your own fields and the type threads through `item()`, `queue()`, and every event payload that carries an item.

## The video element

`this.player.videoElement` is the raw `<video>` element. It is `undefined` until the first `backend()` call constructs the backend, so guard the read:

```ts
const videoEl = this.player.videoElement;
if (videoEl) {
	this.listen(videoEl, 'enterpictureinpicture', () => this.applyPipIcon(true));
	this.listen(videoEl, 'leavepictureinpicture', () => this.applyPipIcon(false));
}
```

That snippet is how `DesktopUiPlugin` tracks PiP: native element events through the scoped `listen()` from the [handbook](/nomercy-player-core/handbook/listening), so the listeners unwind on dispose.

Read from the element when the player surface has no answer yet. `DesktopUiPlugin` resolves duration in three steps: `player.duration()`, then its own cached value, then `videoElement.duration` as the last fallback.

## Video geometry: videoRect()

The video renders with `object-fit: contain`, so the displayed picture is usually smaller than the container. `videoRect()` returns the displayed content rectangle relative to the player container, or `null` before video dimensions are known. Changes are signaled by the `'videoRect'` event.

Overlay plugins that align to the picture (a subtitle renderer, a zone highlighter) use this instead of computing their own letterbox math. `SubtitleOverlayPlugin` consumes exactly this pair.

```ts
this.on('videoRect', ({ rect }) => {
	if (!rect)
		return;
	this.box.style.left = `${rect.left}px`;
	this.box.style.width = `${rect.width}px`;
});
```

## The track surfaces

Three surfaces follow the same read-list, read-selection, select shape:

| Surface | List | Read selection | Select |
| ------- | ---- | -------------- | ------ |
| Subtitles | `subtitles()` | `subtitle()` returns `{ index, track }` or `null` | `subtitle(idx)`, `subtitle(null)` for off |
| Audio | `audioTracks()` | `audioTrack()` | `audioTrack(idx)` |
| Quality | `qualityLevels()` | `quality()` returns `'auto'` or `{ index, ... }` | `quality(idx)`, `quality('auto')` |

And the events that drive a UI built on them:

| Event | Fires when |
| ----- | ---------- |
| `subtitle` | The active subtitle selection changed |
| `subtitles` | The subtitle track list changed without a reload (`addSubtitleTrack()` / `removeSubtitleTrack()`) |
| `audioTrack` / `audioTracks` | Audio selection changed / list changed |
| `quality:requested` | Someone picked a level (or auto) |
| `level-switched` | The stream actually changed level, which in auto mode happens without any pick |
| `levels` | The quality level list changed |
| `mediaReady` | The new item finished loading; the reconcile point |

`mediaReady` is where a track UI reconciles its cached indexes with the player's canonical state. `DesktopUiPlugin` reads `subtitle()`, `audioTrack()`, and `quality()` there rather than guessing from track defaults, because plugin-rendered tracks (ASS via Octopus) never appear in the backend's native lists.

Two quality facts trip up every hand-rolled quality menu:

- Requested and playing are different values. `quality()` stays `'auto'` while `level-switched` reports what is actually on screen. `DesktopUiPlugin` caches the playing index from `level-switched`, and before the first one lands it peeks `player.backend()?.currentLevel?.()`.
- `qualityLevels()` filters unsupported codecs, so match a level by its `index` field, not by array position.

Runtime subtitle injection is a first-class surface:

```txt
addSubtitleTrack(track: SidecarSubtitleInput, opts?: ActionOptions): KitSubtitleTrack;
removeSubtitleTrack(id: string, opts?: ActionOptions): void;
```

`addSubtitleTrack()` injects a sidecar track into the currently playing item with no reload. It is idempotent by `url` plus normalized `language`, and selects the track immediately when you pass `default: true`. Both methods fire the `subtitles` event, which is your cue to recheck any content-gated UI.

## Chapters

`chapters()` returns the current item's chapter list, each entry `{ index, start, end, title }` in seconds. `seekToChapter(idx)` jumps to one and emits `'chapter'`. The `'chapters'` event announces list changes.

Chapter markers need the duration too, so render on both signals, whichever arrives last:

```ts
this.on('chapters', () => this.renderChapterMarkers());
this.on('duration', () => this.renderChapterMarkers());
```

For previous/next navigation, `DesktopUiPlugin` uses a one-second tolerance. "Previous chapter" is the last chapter whose `start` is before `time - 1`. So pressing it inside the first second of a chapter goes to the chapter before it, instead of restarting the current one. "Next" is the first chapter whose `start` is after `time + 1`.

## Display states

Fullscreen, PiP, and theater are accessor pairs plus toggles plus events:

```txt
fullscreen(): FullscreenState; // toggleFullscreen(), 'fullscreen' event with { active }
pip(): PipState;               // togglePip(), 'pip' event
theater(): TheaterState;       // toggleTheater(), 'theater' event
aspectRatio(): Stretching;     // cycleAspectRatio(), 'aspectRatio' event
```

Fullscreen enters on the player container, not the video element, so everything a plugin mounted on the container comes along into fullscreen. No re-parenting is needed.

The states interact, and a UI plugin has to compose them. `DesktopUiPlugin`'s rule is worth copying. Theater is meaningless inside fullscreen or PiP, so the theater button hides whenever either is active. PiP chrome floats over another window, so navigation buttons hide there too. A config opt-out always wins over state-driven showing.

## The overlay stack

The player container (`.nomercyplayer`) is `position: relative` with the `<video>` at `z-index: 0`. Every `mount()` call appends a `<div>` to that container, in call order. Stacking above the video is a matter of your own stylesheet: absolute positioning plus a `z-index`.

`DesktopUiPlugin` claims one mount named `overlay` and puts its whole chrome inside it, at `z-index: 20`. The root is `pointer-events: none`; the bars and buttons re-enable pointer events on themselves. Inside that root:

```text
overlay                       z-index 20 on the container
  top-bar                     back / cast / close, title
  center                      spinner + center play button
  bottom-bar                  slider bar + button row
  menu-frame-dialog           a <dialog>, the settings menus
  keybinds overlay            the ? shortcuts dialog
```

So your own mount coexists with the desktop UI by picking a layer:

- Below `20`: your element renders under the chrome. Right for content-anchored overlays (a subtitle layer, a watermark).
- Above `20`: your element renders over the chrome. Right for modal surfaces of your own.
- Inside the chrome: append into `player.getPlugin(DesktopUiPlugin)?.overlay()` and your element inherits the auto-hide lifecycle instead of floating over hidden bars. See [the desktop UI page](/nomercy-video-player/plugins-adapters/desktop-ui) for `overlay()`, `holdChrome()`, and `releaseChrome()`.

## Who owns activity

The player has built-in activity tracking. It watches its own container for pointer, touch, and key input, emits the `activity` event, and keeps `.active` / `.inactive` classes on the container. A plugin whose UI should fade with the controls needs no timer at all; it keys visibility off those classes in CSS.

A UI plugin that brings a richer activity state machine takes over as the sole emitter with `activityTracking(false)`. `DesktopUiPlugin` does exactly this in `use()`, because open menus, hover, and scrubbing all pin its chrome, and hands ownership back at teardown:

```ts
this.player.activityTracking(false);
this.lifecycle.addCleanup(() => this.player.activityTracking(true));
```

Do not run a second activity timer next to the desktop UI. React to the `activity` event or the container classes, and if your overlay must pin the chrome, use `holdChrome()` / `releaseChrome()`.

## Taking over the screen

A plugin that needs the whole screen (a disc-menu interpreter painting the disc's own chrome) does not fight the desktop UI. It disables it:

```ts
const ui = this.player.getPlugin(DesktopUiPlugin);
ui?.disable('disc-menu');
// later
ui?.enable();
```

`disable()` hides the overlay outright, cancels the inactivity timer, and emits one final `activity: false`. `enable()` restores it and re-arms auto-hide.

## Surfaced intents: back, close, cast

The desktop UI's top-bar buttons emit player events and do nothing else. `back` and `close` buttons appear only while a listener for their event is registered. The `listeners-changed` event keeps that in sync live. `cast` is an option-gated button that emits `'cast'` instead. All three are handled in the consumer, not in a plugin:

```ts
player.on('back', () => router.back());
player.on('cast', () => openDevicePicker());
```

## Extending a built-in plugin

A subclass that keeps the same `static id` replaces the built-in at registration:

```ts
import { KeyHandlerPlugin } from '@nomercy-entertainment/nomercy-video-player/plugins';

class MyKeyHandler extends KeyHandlerPlugin {
	static override readonly id = 'key-handler'; // same id = replaces the built-in

	protected override addPlaybackKeys(): void {
		super.addPlaybackKeys();
		this.bind('n', player => player.next({ source: 'user' }));
	}
}

player.addPlugin(MyKeyHandler);
```
