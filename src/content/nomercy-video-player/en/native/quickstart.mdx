title: Native quickstart

The native video player is the same library as the web one, ported rather than
reimplemented.

Same method names, same events, same error codes. All of it generated from one
contract and checked against it on every build.

What differs is the toolkit underneath. Android and the desktop draw in Compose,
Apple draws in SwiftUI. Both mount the same engine.

## Android and desktop

One coordinate for the engine, one for the chrome. An application that already
draws its own controls takes the first and leaves the second.

```kotlin
dependencies {
    implementation("tv.nomercy:nomercy-video-player-kmp:0.2.14")
    implementation("tv.nomercy:nomercy-video-player-compose:0.2.14")
}
```

Then one view. `NMVideoPlayerView` reads the device it is on and mounts the
touch chrome or the focus chrome accordingly, so the same call is a phone player
and a television player with different hands on it.

:::snippet{file="kotlin-quickstart"}
:::

The engine is `ExoPlayerVideoBackend` on Android and `VlcjVideoBackend` on the
desktop. Both implement the same `VideoBackend`, so everything above the seam is
identical and the only per-platform line is the one that constructs the engine.

## What the desktop needs installed

Nothing. The desktop engine decodes through libVLC. libVLC arrives with the
dependency rather than from the machine.

The first time a player is constructed, the library does three things:

- Fetches the prebuilt runtime for that operating system and architecture
- Checks it against the digest it was published with
- Unpacks it into a per-user cache

Later runs read the unpacked copy.

A VLC that happens to be installed is used only when there is no payload for the
platform yet.

That way one build behaves the same on every machine, rather than inheriting
whichever version somebody had lying around.

To supply your own, point `nomercy.player.natives.libvlc.dir` at a directory
holding it. That one is taken instead, with the digest check and download
skipped.

## iOS and tvOS

The Swift package manifest lives in the `apple/NoMercyPlayer` folder of the
repository, not at its root, so SwiftPM cannot resolve it from the repository
URL. Check out a release tag, then add that folder as a local package. Setting
`NOMERCY_SPM_RELEASE=1` makes the manifest download the checksummed engine
framework published with the tag instead of looking for a local build.

```swift
.package(path: "../nomercy-video-player-kmp/apple/NoMercyPlayer")
```

Link `NoMercyPlayer`, the drop-in product, to your target. An application that
draws its own chrome links `NoMercyVideoPlayer`, the headless engine, instead.

`NMVideoChromeView` draws the controls and reads everything it shows off the
object you hand it. `EngineVideoPlayer` is the projection it observes, and it
forwards to anything conforming to `VideoEngine`, which is seven members.

:::snippet{file="swift-quickstart"}
:::

Apple gets SwiftUI rather than Compose because an application already drawing
its chrome in SwiftUI does not want a second toolkit in the process.
