# The Queue

Behind `queue()` is one cursor-aware `MediaList<T>` instance, the same structure [Core: The Queue](/nomercy-player-core/tour/queue) documents. `nomercy-music-player` adds the item shape (`MusicPlaylistItem`), everything else, the queue mechanics, is unchanged kit code.

## The track shape

`MusicPlaylistItem` carries `name` (the canonical display field, `title` also works since it's inherited from the base shape but `name` is what the rest of this library reads), `artist`, `album`, `cover`, `url`, `lyricsUrl`, and `duration`:

```ts
player.setup({
  baseUrl: 'https://your-server.example.com/api/files',
  playlist: [
    { id: 'track-1', name: 'Where Dreams Drift', artist: 'Ketsa', url: '/K/Ketsa/01 Where Dreams Drift.mp3' },
    { id: 'track-2', name: 'Saviour Above', artist: 'Ketsa', url: '/K/Ketsa/02 Saviour Above.mp3' },
  ],
});
```

`url` stays relative and `baseUrl` supplies the origin, the pattern [Quick Start](/nomercy-music-player/quickstart#the-baseurl-pattern) introduces. There's no `file` → `url` normalization step here, a track is already in its canonical shape the moment it enters the queue. `cover` is resolved differently, see [Now Playing & Lyrics](/nomercy-music-player/build/now-playing) for why cover art usually needs a fully-qualified URL instead.

## Reading and moving the cursor

`queue()` returns the current items as a readonly array; `item()` reads the active item, `item(target)` moves the cursor and loads it. `index()` reads the cursor's position, `queueLength()` its size:

```ts
const items = player.queue(); // ReadonlyArray<MusicPlaylistItem>
const current = player.item();
player.item('track-2'); // by id
player.item(1); // by index
```

`peekNext()` / `peekPrevious()` read what `next()` / `previous()` (see [Transport](/nomercy-music-player/tour/transport)) would load, without moving the cursor or triggering a load, useful for a "coming up next" label or for picking the target of a manual [crossfade](/nomercy-music-player/tour/crossfade).

## Mutating the queue

Every mutation method below fires a typed event (`queue:append`, `queue:move`, ...) that a reactive track-list UI subscribes to instead of re-reading `queue()` after every call.

| Method | What it does |
| --- | --- |
| `queueAppend(item)` | Add to the end. |
| `queuePrepend(item)` | Add to the front. |
| `queueInsert(item, index)` | Add at a specific position. |
| `queueRemove(id)` / `queueRemoveAt(index)` | Remove by id or position. |
| `queueMove(from, to)` | Reorder in place. |
| `queueClear()` | Empty the queue. |
| `queueShuffle()` | Randomize order; the cursor follows the currently-playing track to its new position. |
| `queueSort(compare)` | Sort with your own comparator. |

Removing the item before the cursor decrements the cursor automatically, so it keeps pointing at the same logical track, none of these ever silently jump playback to the wrong entry.

## playItem() and playNow()

`queue(items); item(start); play()` races: `item()` fires a fire-and-forget `load()`, and a `play()` called immediately after can reach the backend before the source is even set. `playItem(target)` and `playNow(items, start?)` exist to close that race, both route through `item(target, { autoplay: true })` internally, which only calls `play()` inside the resolved `load()`'s own continuation:

```ts
player.playNow(album, 'track-2'); // replace the queue and start playing this track
player.playItem('track-1'); // jump to a track already in the queue and play it
```
