# Time & Seeking

Position and duration come straight from `nomercy-player-core`, same as transport. So does the `'time'` event's payload: the kit's full `TimeState` snapshot. A progress bar almost always wants percentage and remaining time in the same read.

## Reading and seeking

`time()` reads the current position in seconds. `time(seconds)` seeks to a new one. There is no separate `seek()`.

Position is reported by two different events, for two different reasons:

| Trigger | Events |
| --- | --- |
| Ordinary playback | Ticks the `time` event per frame, plus the throttled `progress` event. |
| A deliberate jump | Fires the cancellable `beforeSeek` → `seek` → `seeked` cycle. |

It is the same split the web platform draws between `timeupdate` and `seeking`/`seeked`. The tick against the jump:

```ts
import nmplayer from '@nomercy-entertainment/nomercy-music-player';

const player = nmplayer('player');

const currentTime = player.time(); // seconds
await player.time(120); // jump to 2:00
```

`duration()`, `buffered()`/`bufferedRanges()`, and `timeData()` round out playback position. `timeData()` bundles them into one `TimeState` snapshot, computed together so the values agree at the moment of the call instead of drifting across separate reads. Full signatures are on [Reference: Domain Types](/nomercy-player-core/reference/types#time--seek-methods).

```ts
const { position, duration, percentage } = player.timeData();
```

## Relative seeks

`rewind(seconds?)` and `forward(seconds?)` compute a relative target from the current position and run the same cancellable `beforeSeek` → `seek` → `seeked` cycle. Both default to a 5 second step when called with no argument. `restart()` seeks to `0` and resumes playback. That is one atomic intent, not a seek-then-play sequence, so a cancelled seek skips the resulting `play()` too:

```ts
await player.rewind(10); // -10s
await player.forward(30); // +30s
await player.restart();
```

`seekByPercentage(pct)` seeks to a position expressed as `0`-`100` percent of `duration()`. It is the calculation a progress bar's click handler would otherwise have to do by hand.

## The `'time'` event payload

Core's `BaseEventMap` defines `'time'` as the full `TimeState` snapshot: everything a scrubber needs in one payload. The shape is identical across the music and video players:

```ts
player.on('time', ({ time, percentage, position, duration, buffered, remaining }) => {
  scrubber.value = String(time);
});
```

`position` aliases `time`, `percentage` is elapsed time as `0`-`100` of `duration`, `buffered` is seconds loaded ahead, and `remaining` is seconds left. It is the same shape `timeData()` returns, so subscribe to this instead of polling from a render loop. See [Reference: Events](/nomercy-player-core/reference/events#standard-transport) for the full field list.
