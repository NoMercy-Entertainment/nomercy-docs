## Built-in plugin catalog

The music-specific plugins are importable from `@nomercy-entertainment/nomercy-music-player/plugins`.

| Plugin | Plugin id | What it does |
| ------ | --------- | ------------ |
| [`AutoAdvancePlugin`](/nomercy-music-player/plugins-adapters/auto-advance) | `'auto-advance'` | Advances the queue on `ended`; optionally preloads and crossfades on `itemEndingSoon` |
| [`LyricsPlugin`](/nomercy-music-player/plugins-adapters/lyrics) | `'lyrics'` | Fetches and time-syncs lyrics via the cue parser registry; fires `line` / `lineEnter` / `lineExit` |
| [`ScrobblePlugin`](/nomercy-music-player/plugins-adapters/scrobble) | `'scrobble'` | Reports plays to an `IScrobbler` backend on the 50%-or-4-minute rule |
| [`CastSenderPlugin`](/nomercy-music-player/plugins-adapters/cast-sender) | `'cast-sender'` | Chromecast sender with music track metadata and `audio/mpeg` content type |
| [`MediaSessionPlugin`](/nomercy-music-player/plugins-adapters/media-session) | `'media-session'` | Publishes track metadata and artwork to the OS Media Session |
| [`KeyHandlerPlugin`](/nomercy-music-player/plugins-adapters/key-handler) | `'key-handler'` | Core bindings plus `n` next, `p` previous, `r` repeat cycle, `s` shuffle |

The same entry point re-exports the core audio plugins for convenience: `audioGraphPlugin`, `equalizerPlugin`, `mixerPlugin`, `spectrumPlugin`, `canvasPlugin`, `VisualizationPlugin`, `volumeMemoryPlugin`, plus `embedPlugin`, `messagePlugin`, and `tabLeaderPlugin`. None of them allocate an `AudioContext`, canvas, or animation frame unless you register them.

## Typing against the music player

Use `IMusicPlayer` as the `P` generic. It is the stable public contract and adds the music methods (`backend`, `crossfadeTo`, `isTransitioning`, `setTransitionStrategy`) plus the `MusicPlaylistItem`-typed queue and cursor. `NMMusicPlayer` is the concrete class; prefer the interface so your plugin does not depend on the class hierarchy.

```ts
import { Plugin } from '@nomercy-entertainment/nomercy-player-core';
import type { IMusicPlayer, MusicPlaylistItem } from '@nomercy-entertainment/nomercy-music-player';

export class MyMusicPlugin extends Plugin<IMusicPlayer> {
	static override readonly id = 'nomercy:my-music-plugin';

	override use(): void {
		this.on('item', ({ item }) => {
			if (!item)
				return;
			// item is typed as MusicPlaylistItem: name, artist, album, image, lyricsUrl
		});
	}
}
```

`MusicPlaylistItem` gives every plugin `name`, and the optional `artist`, `album`, `url`, `lyricsUrl`, and `duration` fields. Cover art is the inherited `image` field; the shipped plugins read `image` first and fall back to the legacy `cover` field.

## Music-specific events

`MusicEventMap` extends the core `BaseEventMap` with:

- `backend:changed`, after a runtime `backend(kind)` swap. Payload: `{ kind }`.
- `beforeCrossfade`, cancellable. `preventDefault()` stops the fade before any buffer is touched.
- `crossfadePrevented`, fired instead of `crossfadeStart` when a listener cancels.
- `crossfadeStart`, payload `{ from, to, duration }` with `duration` in milliseconds.
- `crossfadeComplete`, payload `{ item }` once the swap has settled.

Everything else, including `item`, `time`, `ended`, and `itemEndingSoon`, is the core event map. See [Listening to events](/nomercy-player-core/handbook/listening).

{/* partial */}
```ts
override use(): void {
	this.on('crossfadeStart', ({ from, to, duration }) => {
		this.showTransition(from?.name, to.name, duration);
	});
	this.on('itemEndingSoon', ({ remaining, item }) => {
		this.prepare(item, remaining);
	});
}
```

## The audio backend

This is the biggest thing a music plugin can reach that a bare core plugin cannot. `this.player.backend()` returns the active `IAudioBackend`. Two implementations ship:

- `AudioElementBackend` (`'audio-element'`), an `<audio>` element with a lazily created media element source. Its crossfade ramp runs on an animation frame loop and is not sample-accurate.
- `WebAudioBackend` (`'webaudio'`), an `<audio>` element routed through an `AudioContext` gain and analyser graph. Sample-accurate transitions.

The backend surface a plugin cares about:

```ts
const backend = this.player.backend();

backend.mediaElement(); // the raw HTMLMediaElement. Cast SDKs bind here.
backend.captureStream(); // MediaStream capture for clip and record plugins
backend.outputNode(ctx); // tail of the backend's internal graph, chain entry point
backend.analyserSource(ctx); // node to tap for analysis
backend.analysisNode?.(ctx); // pre-volume raw source, WebAudioBackend only
backend.supportsCrossfade(); // both built-ins return true
```

`analysisNode` is optional on the contract. When the backend has one, analyser taps placed there read magnitudes before the volume gain, so FFT data does not shrink when the user turns the volume down. `AudioElementBackend` omits it; consumers fall back to `outputNode`.

A runtime swap is `await this.player.backend('webaudio')`. The old backend is disposed, the new one is wired, and the player emits `backend:changed`.

The backend also emits its own events, separate from the player's. `backend.on('backend:sourceswap', fn)` fires after a crossfade promotes the secondary element. The payload carries the new `sourceNode` and, when available, the new `analysisNode`.

Any plugin that holds a reference to a backend audio node must re-mount on this event. Otherwise it ends up wired to a dead node. `AudioGraphPlugin` does exactly this. `IAudioBackend` and the backend event types are exported from `@nomercy-entertainment/nomercy-music-player/adapters`.

## Tapping the analyser and spectrum data

Do not build your own analyser chain. The core audio plugins layer on top of the backend, and the music player re-exports all of them:

```ts
player
	.addPlugin(audioGraphPlugin, { fftSize: 2048 })
	.addPlugin(spectrumPlugin)
	.addPlugin(canvasPlugin)
	.addPlugin(MyVisualization);
```

`AudioGraphPlugin` is the foundation. It owns the `AudioContext` and the signal chain, and every other audio plugin declares it in `requires`. On a `WebAudioBackend` it reuses the backend's context; that is the single-context invariant, backend context, player context, and plugin context are the same object. It taps its shared `AnalyserNode` on the backend's pre-volume `analysisNode` when one exists.

`SpectrumPlugin` reads that analyser once per animation frame and emits a `frame` event. The payload is a full `VisualizationFrame`: byte and float FFT data, waveform samples, band energies (bass, mid, treble), peak-hold values, `sampleRate`, `binHz`, and `peakHz`. Your plugin consumes it with the typed plugin-to-plugin listener:

```ts
import { SpectrumPlugin } from '@nomercy-entertainment/nomercy-music-player/plugins';

export class BeatFlashPlugin extends Plugin<IMusicPlayer> {
	static override readonly id = 'nomercy:beat-flash';
	static override readonly requires = [SpectrumPlugin];

	override use(): void {
		this.on(SpectrumPlugin, 'frame', ({ frame, energy }) => {
			if (energy.bass > 0.8)
				this.flash();
		});
	}
}
```

For raw access, `this.player.getPlugin(SpectrumPlugin)` exposes `analyser()`, `currentFrame()`, and `bandEnergy(loHz, hiHz)`. For custom effect nodes, `getPlugin(AudioGraphPlugin)` exposes `insertEffect(node, 'pre' | 'post')`, `removeEffect(node)`, and `route(from, to)`; every inserted node is disconnected on dispose. Visual output goes through `CanvasPlugin` renderers or a `VisualizationPlugin` subclass, so you never run your own animation frame loop.

## Equalizer and mixer hooks

`EqualizerPlugin` inserts a pre-gain node and a bank of peaking filters into the graph. `MixerPlugin` adds master gain and stereo pan at the tail. Both require `AudioGraphPlugin` and both persist through the plugin storage facade when given a `persistKey`.

A plugin that reacts to EQ changes listens the same way as above:

```ts
this.on(EqualizerPlugin, 'change', ({ bands, selectedPreset }) => {
	this.syncUi(bands, selectedPreset);
});
```

An EQ control surface calls the instance instead: `band(freq, gain)`, `preGain(gain)`, `preset(name)`, `presets()`, `reset()`, `addCustomPreset(preset)`, plus the `bandSliderMin` / `bandSliderMax` / `bandSliderStep` / `bandSliderValue` helpers for building sliders. The mixer instance exposes `gain(dB)`, `pan(value)`, and `muted(value)`.

## Crossfade awareness

Crossfade is on by default. The music `setup()` wrapper injects `crossfadeEnabled: true`, a `MusicPreloadStrategy`, and a `CrossfadeTransitionStrategy` with an equal-power curve unless your config supplies its own. `crossfadeDefaults` in the config sets the fallback duration and curve for every fade.

What a plugin gets:

- `this.player.crossfadeTo(item, opts?)` starts a dual-buffer fade. It resolves the item URL through the player's URL resolver pipeline, the same seam `load()` uses, so hand it a raw item with a relative URL.
- `this.player.isTransitioning()` is `true` while a fade is in flight. Calls to `crossfadeTo` during that window return without doing anything.
- The four crossfade events above, plus `itemEndingSoon` as the trigger signal.
- A `beforeCrossfade` listener may swap `data.to` for a different item; the fade then targets the swapped item.

`crossfadeTo` throws `StateError('core:player/crossfade-unsupported')` when the active backend reports `supportsCrossfade() === false`. After the fade completes the player moves its cursor to the new item, so `item` fires and downstream plugins follow.

`AutoAdvancePlugin` is the reference pattern. It listens to `itemEndingSoon` and resolves what plays next, from queue order or a custom `IPlaylistGenerator`. It optionally preloads that item into the next slot with `load(next, { slot: 'next' })`, then hands off to `crossfadeTo`.

## Audio output devices

The output device surface lives on the player, so any plugin can build a device picker:

- `audioOutputs()` enumerates devices of kind `audiooutput`. Browsers gate the labels behind a permission grant.
- `selectAudioOutput()` opens the browser's own picker (Chrome 105 and later) and triggers that grant. Returns `null` when the user cancels.
- `audioOutput()` reads the current sink id, `null` for the system default. `audioOutput(deviceId)` routes audio via `setSinkId` on the backend's media element.

Unsupported browsers get a structured `BrowserPolicyError`, not a silent no-op. There is no player event for a device switch; a picker plugin updates its own UI after its `audioOutput(deviceId)` call resolves.

## Lyrics data

`LyricsPlugin` is the lyrics surface. On every `item` event it resolves the track's `lyricsUrl`, or asks a custom `getLyricsUrl` resolver. It fetches the file through the auth-aware plugin fetch and parses it through the player's cue parser registry. Then it attaches a `CueTracker` to the clock.

Consume it from another plugin:

```ts
this.on(LyricsPlugin, 'line', ({ text }) => {
	this.renderLine(text);
});
```

Or pull state from the instance: `current()` is the active line payload, `all()` is the full cue list, `fetchLyrics(url)` loads explicitly, and `clear()` drops the tracker without disposing the plugin. `lineEnter` and `lineExit` bracket each line; `loaded` fires once per track with the cue count.

The registry side is core: `player.registerCueParser(parser)` adds a format, and the handbook's [network page](/nomercy-player-core/handbook/network) covers the fetch pipeline the plugin uses. `MusicPreloadStrategy` also lists the lyrics sidecar as a preload asset, next to the media and the cover art, so lyrics for the upcoming track are usually warm.

## Where UI mounts live

The music player is headless. There is no video surface and no overlay stack; `player.container` is the element you handed to `nmplayer(id)`, and the backend's `<audio>` element lives inside it.

- Plugin UI mounts into `this.player.container` through the handbook's [DOM helpers](/nomercy-player-core/handbook/building-dom).
- `CanvasPlugin` mounts its `<canvas>` into the player container by default, or anywhere else via its `mount` option (a CSS selector or an element). It sets `pointer-events: none` so a visualizer never blocks the app.
- `setup({ controls: true })` flips on the native `<audio controls>` bar, which is useful before any UI plugin exists.

## Patterns from the shipped plugins

Three patterns cover most music plugins:

**Subclass the core plugin.** `MediaSessionPlugin`, `KeyHandlerPlugin`, and `CastSenderPlugin` are thin subclasses of their core counterparts. Each overrides one or two protected hooks:

- `getMetadata(item)` maps `name` / `artist` / `album` into OS metadata.
- `addMediaKeys()` adds bindings on top of the inherited set.
- `defaultContentType()` and `buildMetadata(item, ctors)` shape the Cast payload.

Copy this shape when you need a variant of an existing plugin rather than a new one.

**Accept a port, ship a no-op.** `ScrobblePlugin` does no I/O itself. It tracks listened seconds against `time` / `item` / `ended` and calls an `IScrobbler` you supply in options. The default is `NoopScrobbler`, so the plugin is inert until a real backend (Last.fm, ListenBrainz, the NoMercy server) is wired in. `AutoAdvancePlugin` does the same with `IPlaylistGenerator` for custom queue ordering. Both ports are exported.

**Guard the item type.** Plugin `item` payloads are typed against the base item when the plugin's generic is free. The shipped plugins narrow with a small predicate (`'name' in item`) before touching music fields. One internal detail worth knowing: the scrobble tracker only counts time deltas under two seconds, so seeks and track changes never inflate listened time.

The player class internals (`WireInternals`, the phase fields, `_dispatchBefore`) are not exported and not a plugin surface. If you find yourself needing them, the hook you want is almost always one of the `before*` events or a strategy (`setTransitionStrategy`, `setPreloadStrategy`) instead.
