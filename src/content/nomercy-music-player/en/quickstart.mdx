# Quick Start

Five steps to a track playing in your own page. Each one says what you should see, so you can tell it worked before moving on.

## 1. Install it

```bash
npm install @nomercy-entertainment/nomercy-music-player
```

That is the whole install. `nomercy-player-core` arrives with it as an ordinary dependency, so there is no peer dependency to add by hand.

Nothing else arrives with it. The package ships no stylesheet, so there is none to import at any point.

## 2. Give it a container

The player mounts into an element you provide.

```html
<div id="player"></div>
```

That div becomes the player root.
`setup()` marks it `str nomercyplayer` and keeps state classes on it as playback changes, so `str playing` and `str paused` are available to your own CSS without a line of JavaScript.

**It must be a `<div>`.**
Any other tag throws `str core:player/element-not-div`, and an id matching no element throws `str core:player/element-missing`.

The player creates its own `<audio>` element inside that div. Put an `<audio>` in there yourself and it uses that one instead.

Size it yourself. There is nothing to lay out until you add controls, and the whole visible height at this stage is whatever the audio element takes.

`controls: true` is what puts that bar there. It sets `key controls` on the audio element, which is the browser's own transport rather than anything the package draws.

The cover is not the player's doing. Nothing in the package puts artwork on screen, so the last function in the block paints it onto the container itself.

`key name` is the field a music item is displayed by, not `key title`. It is what the cast and media-session plugins read for the track's title, and with `key id` it is one of the two fields the type requires.

Calling `nmplayer('player')` again with the same id gives back the same player rather than a second one. That is what makes it safe inside a component that re-renders.

A real second player therefore needs a second container with a different id.

## 4. Wait for it before calling anything

`setup` returns the player straight away, and it is not usable yet. That is what the `await player.ready()` line is for.

`ready()` resolves once setup has finished and every plugin has come up.

**Past that line every method is safe to call.** Restoring a saved position or selecting a track belongs after it.

Calling `setup` a second time throws `str core:lifecycle/already-setup`, so a half-configured instance is not a state you can reach.

## 5. Nothing plays until something asks it to

This is the one place a video habit misleads you. `cls MusicPlayerConfig` has no `key autoPlay` field, and no config value starts playback.

What `setup` does instead is arm the queue. Once `ready()` resolves it selects the first item with autoplay off, so the player never sits there blank.

Starting it is then a separate call. `player.play()` after `ready()` is one way, and `item(target)` is the other, because selecting an item starts it by default.

That default is why the example passes `{ autoplay: false }`. It wants the track armed and the page quiet until you press play.

## Keep item paths relative

`key baseUrl` is the one config field every playlist should set. It prefixes media and sidecar paths, and `key baseImageUrl` does the same for artwork.

Both are string prefixes joined by plain concatenation, so give the base no trailing slash and the path a leading one.

**Artwork gets its own base because it has to end up absolute.** The operating system's now-playing panel and a Cast receiver both fetch it with no page to resolve against.

An item that carries a full URL of its own is passed through untouched, which is why the cover in the example ignores both bases. The two mix freely and each path is judged on its own.
