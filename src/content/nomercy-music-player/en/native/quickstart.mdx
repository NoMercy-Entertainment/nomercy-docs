The native music player is the same library as the web one, ported rather than
reimplemented.

The port matches the web version on three things: method names, events, and
error codes. All of it is generated from one contract and checked against it
on every build.

What differs is the toolkit underneath. Android and the desktop draw in Compose,
Apple draws in SwiftUI. Both mount the same engine.

## Android and desktop

One coordinate for the engine, one for the chrome. An application that already
draws its own controls takes the first and leaves the second.

```kotlin
dependencies {
    implementation("tv.nomercy:nomercy-music-player-kmp:2.0.0-rc.1")
    implementation("tv.nomercy:nomercy-music-player-compose:2.0.0-rc.1")
}
```

Then the two surfaces a music app needs. `MiniPlayer` is the bar that sits at
the edge of every screen. `FullPlayerScreen` is what `MiniPlayer` expands into.
Both read one `MusicChromeState` and send one set of commands, so the two can
never disagree about what is playing.

```kotlin
val player = NMMusicPlayer(backend)
val chrome = rememberMusicChrome(player)

MiniPlayer(state = chrome.state, commands = chrome.commands)
```

## iOS and tvOS

Add the Swift package and take the drop-in product.

```swift
.package(url: "https://github.com/NoMercy-Entertainment/nomercy-music-player-kmp.git", from: "2.0.0")
```

The SwiftUI half mirrors the Compose one name for name: `MiniPlayer` and
`FullPlayerScreen` over the same state. `MusicScrubber` and `QueueList` are the
pieces underneath. When an application already draws its chrome in SwiftUI, it
does not want a second toolkit in the process, so Apple gets SwiftUI rather
than Compose.
