# Adapter: Translator

`cls ITranslator` is the engine every `fn t` call lands in. The kit ships `cls DefaultTranslator`, a key lookup with `str {var}` interpolation over a table of bundles, seeded with its own `str core.` strings.

Swap the whole engine when your application already runs one and you want the player reading from the same place your interface does. [i18n](/nomercy-player-core/tour/i18n) covers translation day to day, and this page is the reference for the port itself.

## The interface

```ts
interface ITranslator {
	t(key: string, vars?: Record<string, string>): string;
	language(): string;
	language(lang: string): Promise<void>;
	addTranslations(bundle: Translations): void;
	translation(lang: string, key: string): string | undefined;
	translation(lang: string, key: string, value: string): void;
	removeTranslations(prefix: string, lang?: string): void;
	dispose(): void;
}
```

A `cls Translations` bundle is a language tag mapped to a flat table of key and value. `fn translation` answers `ts undefined` for a key it does not hold, which is how a caller tells an absent key from an empty one.

## Default implementation

`fn t` resolves a key by walking the BCP-47 chain of the active language, most specific first, then the fallback language. So `str pt-BR` reads a `str pt` bundle for anything the regional file leaves out, and English after that. A key nothing holds reaches `fn onMissingTranslation` when one is configured, and otherwise comes back as the key itself.

Interpolation runs last. `fn t` with no `key vars` returns the template untouched, and a placeholder your map has no entry for stays in the string as `str {name}`.

`fn setup` builds this translator from four of its own fields:

| Field | Effect |
|---|---|
| `key language` | The starting tag. `str en` when omitted. |
| `key translations` | Bundles merged over the kit's own. A key you set wins the collision. |
| `key loadTranslations` | An async loader for a tag not yet fetched. It runs alongside the kit's loader, and yours wins the same key. |
| `key onMissingTranslation` | The last stop before a key is returned as itself. |

English is seeded at construction so `t('core.network.offline')` answers before any fetch. Every other language the kit ships loads the first time `fn language` switches to it, and a switch to `str pt-BR` loads `str pt-BR` and `str pt` together.

`cls DefaultTranslatorOptions` carries one more field the setup config has no route to: `key fallbackLanguage`, `str en` by default. Pass `ts null` to rely on the BCP-47 parent chain alone, by building the translator yourself and handing it over as `key translator`.

## What the player asks of a custom engine

Passing `key translator` gives your engine the whole job. The kit seeds it with nothing: no `str core.` strings, no `key translations`, no `key loadTranslations`, no starting `key language`. Wire those into the adapter before you pass it.

It still receives everything the player and its plugins produce at runtime:

- `player.language(tag)` dispatches `str beforeLanguage`, calls `fn language` on your engine, loads each registered plugin's bundle for the tag and its parents, and emits `str language`. A listener that prevents the dispatch leaves the language alone and gets `str languagePrevented`.
- Plugin bundles arrive through `fn addTranslations`, already namespaced under `str plugin.` and the plugin's id.
- Disposing a plugin calls `fn removeTranslations` with that prefix and no language, so implement it or plugin strings pile up for the life of the page.
- `player.t(PluginClass, 'label')` builds the same namespaced key before it reaches you.

## Where to import it from

```ts
import { DefaultTranslator } from '@nomercy-entertainment/nomercy-player-core';
import type { DefaultTranslatorOptions, ITranslator } from '@nomercy-entertainment/nomercy-player-core';
```

All three are on the `./adapters/translator` subpath as well, beside the loader helpers `fn translationsFromGlob` and `fn createNetworkTranslationLoader`.

## Rules & restrictions

- `fn language` with a tag answers a `ts Promise`, because an engine may wait on a loader. Await it rather than reading the new strings on the next line.
- `fn addTranslations` merges keys without marking the language fetched, so a later `fn language` for that tag still calls your loader. That is what lets a plugin add strings early without canceling the real load.
- A loader that throws is swallowed and the switch completes, leaving whatever bundle was already in memory.
- `fn dispose` is yours to implement. The default drops every bundle and forgets which languages were loaded.

## How to extend it

Implement the eight members over your own engine and name the instance at setup:

```ts
import nmplayer from '@nomercy-entertainment/nomercy-video-player'; // nomercy-music-player's factory works identically
import type { ITranslator } from '@nomercy-entertainment/nomercy-player-core';

const adapter: ITranslator = myI18nextAdapter;

const player = nmplayer('player');

player.setup({ translator: adapter });
```

The player never checks which implementation is behind the port, so an engine with pluralization, gender or ICU MessageFormat serves `fn t` exactly as the built-in one does.
