# Adapter: Storage

`cls IStorage` is the port the kit saves through: equalizer bands, mixer levels, remembered volume, the viewer's language picks, and anything else a plugin keeps under `ts this.storage`. [Swap an Adapter](/nomercy-player-core/recipes/swap-an-adapter) replaces it end to end and reads back through a plugin. This page is the reference for the port itself.

## The interface

```ts
interface IStorage {
	get(key: string): string | null | Promise<string | null>;
	set(key: string, value: string): void | Promise<void>;
	remove(key: string): void | Promise<void>;
	getJSON<T>(key: string): T | null | Promise<T | null>;
	setJSON<T>(key: string, value: T): void | Promise<void>;
}
```

Every method may answer directly or with a `Promise`, so one interface covers a synchronous store and an asynchronous one.

`fn getJSON` answers `str null` both for a key that is absent and for a value that does not parse, and the two are indistinguishable from the outside. `fn setJSON` writes nothing when the value carries a cycle `JSON.stringify` cannot follow.

## Shipped implementations

| Class | Behavior |
|---|---|
| `cls LocalStorageBackend` | The default. Synchronous, over `localStorage`. Probes the store once at construction and keeps an in-memory map for one that is missing, blocked or full. |
| `cls MemoryStorageBackend` | A map and nothing more. Nothing outlives the page. For tests and server-side rendering. |
| `cls IndexedDBBackend` | Asynchronous, and sized for values `localStorage` will not hold. Its constructor takes `key dbName`, `key storeName` and `key version`, defaulting to `str nomercy-player`, `str kv` and `1`. |

## Where the keys land

A plugin never sees the raw backend. `cls Plugin` hands it a view that prefixes every key with `str nmplayer-`, the plugin's id, and a dash, so two plugins both saving under `str theme` never meet. A plugin with `str probe` for an id writing `str theme` produces `str nmplayer-probe-theme` in the store underneath.

Everything else writes the key you give it, unchanged. The video player keeps the viewer's language picks under `str nmplayer-language-audio` and `str nmplayer-language-subtitle`, and it reaches the backend only when `fn setup` was handed one. Pass `key storage` and those picks survive a reload.

## Where to import it from

```ts
import { IndexedDBBackend, LocalStorageBackend, MemoryStorageBackend } from '@nomercy-entertainment/nomercy-player-core';
import type { IStorage } from '@nomercy-entertainment/nomercy-player-core';
```

All four names are on the `./adapters/storage` subpath as well.

## Rules & restrictions

- `cls IndexedDBBackend` opens its database on the first method call rather than at construction, so building one under Node or during server-side rendering is safe. The first `fn get` there rejects with a `cls BrowserPolicyError` carrying `str core:policy/indexedDBUnsupported`.
- The kit's own persisted plugins read once as they start, and keep the answer only when it is already a value. Equalizer, mixer and volume memory therefore restore their saved state from a synchronous backend. Writes travel through either kind.
- `cls LocalStorageBackend` never throws. A blocked or full store falls through to its map, so a value written this session still reads back and nothing carries into the next page load.
- `cls IStorage` says nothing about where the bytes go. A remote store that syncs one viewer's settings across devices satisfies it exactly as `localStorage` does.

## How to extend it

Implement the five methods over any store you like, then name the instance at setup. This one scopes every saved value to the browser tab:

```ts
import type { IStorage } from '@nomercy-entertainment/nomercy-player-core';

class SessionStorageBackend implements IStorage {
	get(key: string) {
		return sessionStorage.getItem(key);
	}

	set(key: string, value: string) {
		sessionStorage.setItem(key, value);
	}

	remove(key: string) {
		sessionStorage.removeItem(key);
	}

	getJSON<T>(key: string): T | null {
		const raw = sessionStorage.getItem(key);
		if (raw === null) return null;
		try {
			return JSON.parse(raw) as T;
		}
		catch {
			return null;
		}
	}

	setJSON<T>(key: string, value: T) {
		sessionStorage.setItem(key, JSON.stringify(value));
	}
}

player.setup({ storage: new SessionStorageBackend() });
```

Nothing downstream changes. Every plugin goes on calling `ts this.storage` and gets its own namespaced slice of whatever you passed.
