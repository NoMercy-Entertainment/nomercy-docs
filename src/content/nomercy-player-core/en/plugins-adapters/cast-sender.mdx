# Plugin: Cast Sender

`CastSenderPlugin` (id `'cast-sender'`) bridges player transport state to and from an active Chromecast session via the Cast Web Sender SDK. It's written as a shared base class: `nomercy-video-player` and `nomercy-music-player` each subclass it, overriding the two methods that differ per medium.

## Options

| Option | Type | Default | Purpose |
|---|---|---|---|
| `chromecastAppId` | `string` | — | Your registered Cast receiver app id. |
| `enableAirPlay` | `boolean` | — | Also surface an AirPlay control path. |
| `customReceiverNamespace` | `string` | — | Custom message namespace for a non-default receiver. |
| `resumeLocalOnDisconnect` | `boolean` | `true` | Resume local playback when the Cast session ends. |
| `defaultContentType` | `string` | subclass's `defaultContentType()` | MIME type hint sent to the receiver. |
| `live` | `boolean` | `false` | Marks the content as a live stream for the receiver UI. |

## Events

The plugin fires six events across the session's lifecycle:

| Event | Payload |
|---|---|
| `cast:connected` | `{ deviceName }` |
| `cast:disconnected` | none |
| `cast:error` | `{ error }` |
| `cast:remote-state` | `{ time, state }` |
| `cast:media-changed` | `{ contentId }` |
| `unsupported` | `{ reason }` |

## Rules & restrictions

- Chrome/Chromium Web Sender SDK only. In Firefox, Safari, or a non-Chromium browser, `connect()` emits `unsupported` and throws a `BrowserPolicyError` (`core:policy/castUnavailable`). Everything else stays a harmless no-op rather than crashing.
- The plugin requires the global `cast.framework` / `chrome.cast.media` SDK to already be loaded on the page. It does not load the script for you.
- Volume arrives on the kit's own 0-100 `volume()` scale. The plugin divides it to the 0-1 float range the receiver's SDK expects.
- `buildMetadata()` reads only fields defined on the canonical playlist item type. It never casts to a richer intersection to reach a consumer's own fields. Carrying application-specific fields beyond the canonical item? Subclass and override `buildMetadata()` yourself.
- `transferTo('cast')` and this plugin are separate, unlinked mechanisms. `transferTo('cast')` is the kit's own coarse handoff; it drives the Cast SDK directly and knows nothing about `CastSenderPlugin`. Adding this plugin does not wire it into `transferTo()`, and calling `transferTo('cast')` does not go through this plugin's `connect()` / metadata pipeline. Pick one Cast strategy per app.

## Translations

Cast Sender's UI strings (connect/disconnect prompts, error copy) are auto-discovered from the plugin's own `./i18n/*.ts` folder via `translationsFromGlob`. A subclass in `nomercy-video-player` or `nomercy-music-player` ships its own `i18n/` folder too, with only its own keys. The kit's plugin registration walks the prototype chain, so every bundle in the chain ends up in the translation table. See [Core: i18n](/nomercy-player-core/tour/i18n).

## How to extend it

Subclass it and override the two per-medium methods. This is exactly what `nomercy-video-player` and `nomercy-music-player` do, neither reimplements the session/connection handling.

```ts
import nmplayer from '@nomercy-entertainment/nomercy-video-player'; // nomercy-music-player's factory works identically
import { CastSenderPlugin } from '@nomercy-entertainment/nomercy-player-core';

const player = nmplayer('player');

class MyCastSenderPlugin extends CastSenderPlugin {
	protected override defaultContentType(): string {
		return 'application/x-mpegURL';
	}
	// override buildMetadata(item, ctors) for your own item shape
}

player.addPlugin(MyCastSenderPlugin, { chromecastAppId: 'ABCD1234' });
await player.ready();

await player.getPlugin(MyCastSenderPlugin)?.connect();
```
