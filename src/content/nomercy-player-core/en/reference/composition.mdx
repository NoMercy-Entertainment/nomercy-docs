# Reference: Composition Primitives

The three functions [Build a Player](/nomercy-player-core/build/compose-methods) and [Quickstart](/nomercy-player-core/quickstart) use to turn a plain class into something that behaves like `NMVideoPlayer` or `NMMusicPlayer`.

## composeMixins

```ts
function composeMixins<T extends object>(prototype: T, ...modules: object[]): void;
```

Stamps one or more mixin objects onto a prototype, through `Object.getOwnPropertyDescriptors` and `Object.defineProperty`. Getters and setters land as accessors rather than being triggered during the copy.

Collisions resolve left to right: a later module in the argument list wins on the same key. So list specific modules after general ones.

It is idempotent. Calling it twice with the same module overwrites identical descriptors.

## resolvePlayerConstructor

```ts
function resolvePlayerConstructor<C>(
	id: string | number | undefined,
	instances: Map<string, C>,
	className: string,
): PlayerCtorResolution<C>;

type PlayerCtorResolution<C> =
	| { kind: 'existing'; instance: C }
	| { kind: 'mount'; id: string; div: HTMLDivElement };
```

The resolution behind all three factory forms: `nmplayer()`, `nmplayer('div-id')` and `nmplayer(2)`.

- **No id**: returns the first registered instance. Throws `core:player/no-element` on an empty registry.
- **A number**: indexes the registry's insertion order. Throws `core:player/not-found` out of range.
- **A string**: checks the registry first. Failing that, resolves `document.getElementById(id)` and requires a `<div>`. Throws `core:player/element-missing` or `core:player/element-not-div`.

SSR-safe: the `document` call is guarded.

## initPlayerCoreState

```ts
function initPlayerCoreState(player: object, opts: { className: string }): void;
```

Seeds every internal slot (phase `'idle'`, dispatch stack, cue parser registry, play/volume/repeat/shuffle state, volume `100`, playback rate `1`, and the rest) to its canonical starting value. Call this once in your constructor, before the instance is usable.

## KIT_VERSION

```ts
declare const KIT_VERSION: string; // derived from package.json at compile time
```

Compared against a plugin's `static readonly minCoreVersion` at `addPlugin()` time, mismatches throw `core:plugin/incompatible-core-version`.

## playerCoreMethods and the individually-exported mixin groups

`playerCoreMethods` is the `as const` tuple of every shared mixin. It is the exact aggregate both real players compose.

It bundles 26 mixin groups, and 16 of those are importable individually from the public entry.

The other 10 are internal building blocks, meant to be taken as part of the aggregate rather than recomposed piecemeal: stream registration, media tracks, device detection, audio output, cast state, ABR, metrics, loading, activity, and generic DOM helpers.

Individually exported, for composing a narrower surface than the full aggregate:

`lifecycleMethods` · `transportMethods` · `timeMethods` · `volumeMethods` · `queueMethods` · `playQueueMethods` · `stateMethods` · `playerStateMethods` · `pluginRegistrationMethods` · `authMethods` · `i18nMethods` · `cueParserMethods` · `baseUrlAudioContextMethods` · `containerClassEmitMethods` · `preloadStrategyMethods` · `experimentalDescriptor`

```ts
import { composeMixins, lifecycleMethods, transportMethods } from '@nomercy-entertainment/nomercy-player-core';

// A narrower composition than playerCoreMethods — only lifecycle + transport,
// for a consumer building something that genuinely doesn't need the queue,
// i18n, or plugin surface at all.
composeMixins(MyPlayer.prototype, lifecycleMethods, transportMethods);
```

Most consumers want the full `playerCoreMethods` aggregate, as every page in [Build a Player](/nomercy-player-core/build/compose-methods) does, composing a subset is an advanced move for a genuinely minimal use case.
