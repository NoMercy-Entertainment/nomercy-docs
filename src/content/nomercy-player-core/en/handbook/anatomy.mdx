# Core: Anatomy of a Plugin

Every plugin is a subclass of one class. This page walks its full shape: the generics, the static contract, the lifecycle order, and the scoped instances the player hands you.

For the quick tour of the same class, see [The Plugin Base](/nomercy-player-core/tour/plugin-base). This page goes deeper.

## The three generics

{/* partial */}
```ts
class Plugin<
	P extends IPlayer<BaseEventMap> & DispatchTarget = IPlayer & DispatchTarget,
	O = unknown,
	E extends Record<string, any> = Record<string, never>,
>
```

Each slot buys you a different kind of type safety.

`P` is the player type. It feeds `PlayerEventMap<P>`, so `this.on('...')` autocompletes the full event map of the player you target. Type against a concrete player class and you see its events, not just the base set.

`O` is the options type. It types `this.opts`, and it flows through to consumers: `player.addPlugin(YourPlugin, opts)` type-checks the inline options literal against `O` with no cast at the call site.

`E` is the plugin's own event map. It types `this.emit(...)` inside the plugin, and it is what other plugins see through `on(YourPluginClass, 'event', fn)`. The class carries it on a phantom `__events__` property, so it costs nothing at runtime.

## The static contract

Static fields describe the plugin to the registration pipeline before any instance exists.

```txt
static readonly id: string;                                        // required
static readonly description: string;                               // required
static readonly version: string;                                   // defaults to '0.0.0'
static readonly minCoreVersion?: string;
static readonly requires?: ReadonlyArray<RequireSpec>;
static readonly replaces?: string;
static readonly priority: number;                                  // defaults to 0
static readonly translations?: Translations;
```

Each field describes something different about the plugin:

| Field | What it does |
| --- | --- |
| `id` | Names the plugin everywhere: event namespaces, storage keys, logger prefix, mount classes, error scopes. Vendored ids (`'fillz:viz'`) are the rule outside our own packages. |
| `description` | One human-readable line. Plugin listings and error messages show it. |
| `version` | A semver string. Dependency version checks read it. |
| `minCoreVersion` | The lowest kit version the plugin runs on. Registration throws `core:plugin/incompatible-core-version` when the running kit is older. |
| `replaces` | Opts in to a same-id swap. Without it, a duplicate id throws `core:plugin/duplicate-id`. With it, the player disposes the existing plugin with that id first. |
| `priority` | Orders plugins, default zero. `enabledPlugins()` sorts descending, so higher-priority plugins dispatch first. Ties keep registration order. See [Listening](/nomercy-player-core/handbook/listening) for what this means for handlers. |
| `translations` | Ships static i18n bundles under `plugin.<id>.*`. The player merges them in on register and removes them on dispose. For bundles loaded at runtime, override `loadTranslations(lang)` instead. |

`requires` lists dependencies as class references. The plain form is a class. The object form adds `optional` or `minVersion`:

{/* partial */}
```ts
static readonly requires = [
	AudioGraphPlugin,
	{ plugin: MediaSessionPlugin, optional: true },
	{ plugin: SpectrumPlugin, minVersion: '2.1.0' },
];
```

Each dependency check has its own outcome:

| Check | Result |
| --- | --- |
| Missing required dependency | Throws `core:plugin/missing-dep` at registration. |
| Missing optional dependency | Logs a debug warning. The plugin runs anyway. |
| Version below `minVersion` | Throws `core:plugin/version-mismatch`. |

## The lifecycle order

A plugin lives through exactly three steps: `initialize`, then `use`, then `dispose`.

### initialize()

```txt
initialize(player: P, opts: O, lifecycle: LifecycleRegistry): void
```

The player calls this right after constructing your class. You never call it yourself, and you rarely override it. It wires `this.player`, `this.opts`, and `this.lifecycle`, then builds the scoped `this.logger` and `this.storage` (details below).

Nothing of yours should run here. Constructors and `initialize` are for wiring, not behavior.

### use()

```txt
use(): void | Promise<void>
```

This is your setup hook. Wire listeners, claim mount points, start fetches. Everything is available: the player, the options, the logger, the storage, and every helper on the base class.

`use()` may return a promise. The player awaits it before emitting `ready`, bounded by `pluginInitTimeoutMs`. A `use()` that throws or times out fails the registration: the player emits `plugin:failed`, tears the instance down, and disables any plugin that requires yours.

### dispose()

```txt
dispose(): void
```

Override this only for resources the lifecycle registry cannot track: third-party library instances, custom WebGL contexts, non-standard observers.

Everything registered through the helpers is already released before your `dispose()` body runs: listeners, timers, animation-frame loops, observers, abort controllers, mount nodes. Do not re-clean them here.

The kit calls `dispose()` when the player itself disposes, or when the plugin is removed with `player.removePlugin(PluginClass)`.

## enable, disable, enabled

```txt
enabled(): boolean
enable(): void
disable(reason?: string): void
```

Each method does one job:

| Method | What it does |
| --- | --- |
| `enabled()` | Reads the current state. Starts as `true`. |
| `disable(reason?)` | Turns the plugin off without unloading it. |
| `enable()` | Turns the plugin back on. |

Both `enable()` and `disable()` are idempotent. Both emit paired events: `plugin:enabled` / `plugin:disabled` on the bare channel and on the id-namespaced channel (`plugin:<id>:disabled`), with the id and the optional reason in the payload.

Disabling does not detach your listeners. They stay subscribed in either state. Guard your own handlers with `this.enabled()` so a disabled plugin stops reacting.

The kit also disables plugins for you in one case: when a plugin fails to register, every plugin that requires it is disabled with a `dep-failed:<id>` reason, cascading through the dependency tree.

## Where player, opts, logger, and storage come from

`initialize()` assigns all four before `use()` runs. Each one holds something different:

| Property | What it holds |
| --- | --- |
| `this.player` | The player instance that registered you, typed as `P`. |
| `this.opts` | Whatever the consumer passed to `addPlugin(YourPlugin, opts)`, typed as `O`. |
| `this.logger` | A child of the player's configured logger. Output carries the prefix `[nmplayer][<id>]`. |
| `this.storage` | The player's configured storage backend, with a fixed key prefix. |

Everything the consumer configured at `setup()` time is readable through `this.player.options`. The seek-preview tutorial reads `this.player.options.baseUrl` to resolve sprite URLs the same way the player itself does. Prefer the player's methods where one exists (`this.player.baseUrl()` style accessors), and reach into `options` for config that has no accessor.

Read `this.opts` in `use()`. Change it later through `options(partial)`, which shallow-merges and emits `opts:changed`.

Every key you read or write through `this.storage` becomes `nmplayer-<id>-<key>` in the backing store, so plugins never collide with each other or with player-level keys.
