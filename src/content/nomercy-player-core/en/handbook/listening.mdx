# Listening

Inside a plugin, subscribe with helpers that clean up on dispose.
[The Event Bus](/nomercy-player-core/tour/event-bus) already covers the raw player `fn on`, `fn once`, `fn off`, and `fn emit`.
This page is the plugin surface: `fn listen`, plus the two-form helpers that register teardown for you.

## DOM events

`fn listen` is the drop-in for `fn addEventListener` on an `cls EventTarget`.
It records the target, event name, handler, and options.
Dispose removes each listener with those same options.
After dispose, further `fn listen` calls do nothing.

:::snippet{file="core-handbook-listening" lines="63-66" live="false"}
:::

A raw `fn addEventListener` is not in that registry.
Dispose will not remove it for you.

## Player and other plugins

`fn on` and `fn once` share two forms.
The string form listens on the player, for names such as `str item` or `str play`.
The class form listens to another plugin: `on(OtherPlugin, 'beat', fn)`.
That resolves to `plugin:<id>:<event>` on the player bus.

| Form | What it wires |
| --- | --- |
| `fn on` / `fn once` | Player string, or other plugin by class |
| `fn off` | Same forms, early detach |
| `fn hasListeners` | Same forms, pure read |

Both `fn on` and `fn once` call the player bus, then record cleanup that runs `fn off` on dispose.
You do not unsubscribe by hand unless you want to stop early.
If `fn once` never fires, dispose still clears it.

:::snippet{file="core-handbook-listening" lines="51-61" live="false"}
:::

Do not call `fn this.player.on` from a plugin.
That skips the cleanup registration.

## Stop early

`fn off` uses the same two forms.
Pass the same function reference you subscribed with.
Most plugins never call it.
Dispose already removes what these helpers registered.

:::snippet{file="core-handbook-listening" lines="46-50,68-70" live="false"}
:::

## Check before you work

`fn hasListeners` reports whether any named listener is present.
Use it when building a payload costs something.
Skip the work when nobody subscribed.

:::snippet{file="core-handbook-listening" lines="32-34" live="false"}
:::

## Priority order

`key priority` defaults to `0`.
`fn enabledPlugins` returns enabled plugins sorted by priority descending.
Ties keep registration order.
That list order does not reorder handlers on one bus event.
Handlers still run in subscription order.

:::snippet{file="core-handbook-listening" lines="39-40,44,71,133" live="false"}
:::
