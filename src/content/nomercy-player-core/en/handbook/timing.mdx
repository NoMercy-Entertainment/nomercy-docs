# Timing

Inside a plugin, schedule work with helpers that clean up on dispose.
Each helper records its timer, loop, signal, or observer in the plugin's lifecycle registry.
The player builds one registry for every plugin it registers.
Dispose cancels everything in it, whether or not your code remembers.

## One-shot delay

`fn timeout` takes a callback and a delay in milliseconds, like `fn setTimeout`.
Dispose cancels it if it has not fired yet.
A callback that throws is caught and logged to the console, so it cannot stop the player.

`fn timeout` returns a numeric handle.
Most plugins ignore it.
To cancel one timer before dispose, pass the handle to `fn clearTimeout`.

:::snippet{file="core-handbook-timers" lines="31-40" live="false"}
:::

## Repeat on a schedule

`fn interval` takes a callback and a period in milliseconds, like `fn setInterval`.
Dispose cancels it.
A tick that throws is caught and logged, and the next tick still runs.

:::snippet{file="core-handbook-timers" lines="42-45" live="false"}
:::

It returns a numeric handle as well.
Pass it to `fn clearInterval` to stop that one interval early.

## Animation frames

`fn frame` runs a callback on every animation frame.
The callback receives `(deltaMs, time)`.
`var deltaMs` is the milliseconds since the previous frame, so motion keeps one speed at any refresh rate.
The first delta counts from the `fn frame` call.

`fn frame` returns a stop function for that one loop.
Other loops keep running, and dispose still stops every loop.
A frame that throws is caught and logged, and the loop goes on.

:::snippet{file="core-handbook-timers" lines="47-53" live="false"}
:::

Where `fn requestAnimationFrame` is missing, such as Node or server rendering, `fn frame` starts nothing.

## Abort signals

`fn abortable` returns a new `cls AbortController`.
Dispose aborts it.
Pass its `key signal` to any API that accepts one.

The plugin's own `fn fetch` already does this for each request.
Reach for `fn abortable` when you call another signal-aware API yourself.

:::snippet{file="core-handbook-timers" lines="55-63" live="false"}
:::

## Observers

Observers go through `fn this.lifecycle.observe`, the registry itself.
The plugin has no `fn observe` helper of its own.
It takes a `cls ResizeObserver`, `cls MutationObserver`, `cls IntersectionObserver`, or any object with a `fn disconnect` method.

Dispose disconnects it.
`fn observe` returns the observer unchanged, so the call chains straight into its own `fn observe`.

:::snippet{file="core-handbook-timers" lines="65-70" live="false"}
:::

## When to use which

Pick the helper by the kind of work, not by the delay.
Each row cleans up on dispose.

| Work | Helper |
| --- | --- |
| Run once after a delay | `fn timeout` |
| Run every period, such as a save | `fn interval` |
| Draw or animate every frame | `fn frame` |
| Hand a cancel signal to an API | `fn abortable` |
| Watch size, DOM changes, or visibility | `fn this.lifecycle.observe` |

Raw `fn setTimeout`, `fn setInterval`, and `fn requestAnimationFrame` are not in the registry.
Dispose will not cancel them, so they keep running after the plugin is gone.

## Around dispose

The player calls your plugin's `fn dispose` first, then the registry's.
Your timers, loops, signals, and observers are still live inside your own `fn dispose`.
You do not cancel them there.

A helper called after dispose schedules nothing and returns a safe value.
[ILifecycleRegistry](/nomercy-player-core/plugins-adapters/adapter-lifecycle-registry) lists what each call returns then.
