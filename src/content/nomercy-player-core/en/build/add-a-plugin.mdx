# Build a Player: Add a Plugin

Step 2 gave the player something real to drive. This step adds behavior on top of it, without touching `KitPlayer` itself: a plugin.

## Why the player class doesn't change

A plugin extends the player from the outside.

`addPlugin(PluginClass, opts)` queues the plugin before `setup()` runs. Register after `setup()` and the plugin misses its own `use()` call during the pipeline.

In return the plugin gets a scoped logger, namespaced storage and auto-cleaned listeners. [The Plugin Base](/nomercy-player-core/tour/plugin-base) has the full list, and the [Plugin Handbook](/nomercy-player-core/handbook/anatomy) teaches every helper on it in depth.

`KitPlayer`'s composition from steps 1 and 2 needs no change for this. `addPlugin` and `getPlugin` are already in `playerCoreMethods`, stamped onto every kit composition whether you call them or not.

`player.backend().calls` at the end still shows the transport calls from Step 2 (`['play', 'pause', 'play']`), proving the plugin is additive: it observes the same event stream, it doesn't intercept or replace the backend wiring underneath it.

Real players have a declarative shortcut: `setup({ plugins: [PlayCounterPlugin] })`, or `{ plugin: PlayCounterPlugin, opts: {...} }` when it takes options.

That runs through this same `addPlugin()` path at the same moment. It is sugar over the two calls above, not a second mechanism.

`KitPlayer` builds `playerCoreMethods` by hand here for teaching, so this step spells `addPlugin()` out. Both real players support the declarative form.
