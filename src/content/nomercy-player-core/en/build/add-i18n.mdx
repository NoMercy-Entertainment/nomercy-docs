# Build a Player: Add i18n

The last step. Step 3 left a player with a real backend and a registered plugin. This step adds translations, and the class that comes out the other end is the complete one this tutorial was building toward.

## Config, not a separate call

[i18n](/nomercy-player-core/tour/i18n) showed `addTranslations()` merging a bundle into an already-running player. That's the right tool for translations that arrive after setup, loaded from a network bundle or registered by a plugin.

Here, the translations are known upfront. So they go straight into `setup()` alongside `logLevel` and everything else. `language` and `translations` are ordinary `BasePlayerConfig` fields.

The kit ships its own `core.*` strings, so a player has working error and status text before you write a single key. These strings cover:

- Network announcements.
- Auth announcements.
- DRM announcements.
- Accessibility announcements.

English is seeded eagerly at `setup()`, underneath whatever `translations.en` you pass. So `t('core.*')` resolves immediately. A key you do not override falls back to the kit's English.

Every other kit locale loads lazily, the first time `language(lang)` switches to a tag with no bundle seeded. That is the same on-demand mechanism plugin bundles use.

Passing your own static `translations.nl`, as above, seeds that tag directly. It takes over from the kit's lazy `nl` bundle rather than merging with it.

Supplying your own `translator` engine replaces this merge entirely. The kit owns translation state only for its built-in `DefaultTranslator`.
