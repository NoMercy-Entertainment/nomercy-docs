# Plugins

A plugin is a class that extends `cls Plugin`. That is the whole of the definition.

You never construct one yourself.
You hand the class to the player, and the runtime instantiates it, wires it, and tears it down again.

```ts
player.addPlugin(PlayCounterPlugin, { everyNPlays: 2 });
```

The class is the handle for everything afterwards, which is why the class and not an id is what you pass.

`getPlugin(PluginClass)` hands back the live instance typed as that class.
`static requires` names other plugin classes rather than their ids.
`on(PluginClass, 'event', fn)` types the payload from the class you name.

`fn addPlugin` returns the player, so registrations chain.
The `key plugins` array in `setup()` is the same call under another spelling, with identical validation and timing.

## The id is a namespace, not a label

`static id` is the one field every plugin must set, and nearly every other behavior on this page derives from it.

A plugin with `ts id = 'play-counter'` gets these names without asking for them:

| What | Shape |
| --- | --- |
| Logger prefix | `str [nmplayer][play-counter]` |
| Storage keys | `str nmplayer-play-counter-<key>` |
| Mount node class | `str nmplayer-play-counter-<name>` |
| Events | `str plugin:play-counter:<event>` |
| Translation keys | `str plugin.play-counter.<key>` |

Every error the plugin raises carries the same id in its scope, so a report names the plugin that produced it.

Two plugins can therefore do the same thing without ever colliding, and none of them has to remember to prefix anything.

## `use()` is the hook you write

`use()` is the one method a plugin author overrides to do setup work.

The runtime calls it once, after it has wired the instance with the player, your options, the scoped logger and the scoped storage.
It may return a promise, and the runtime awaits it before the player reports itself ready.

The default body is empty, so a plugin that only declares statics needs no `use()` at all.

Subscribing, building DOM, fetching, opening a socket: all of it starts here.

**A plugin that throws from `use()` is torn back down rather than left half-installed.**
The player keeps going without it, and announces the loss on `str plugin:failed`.

`ts this.player` is the player itself, so its methods are yours to call normally.
`ts this.opts` is exactly the object you passed to `fn addPlugin`, and `undefined` when you passed none.

## Helpers, so nothing outlives the plugin

The base class carries a helper for every global a plugin would otherwise reach for.

Every helper that opens something registers the matching cleanup as you call it.
Teardown then releases the lot, and the plugin holds no handles of its own.

- **Listening.** `fn on`, `fn once`, `fn off` and `fn hasListeners`.
- **Timers and observers.** `fn listen`, `fn timeout`, `fn interval`, `fn frame` and `fn abortable`.
- **Speaking.** `fn emit` and `fn dispatchBefore`.
- **Failing.** `fn throw` and `fn report`.
- **Network.** `fn fetch`, `fn websocket` and `fn resolveUrl`.
- **Building.** `fn mount`, `fn createElement`, `fn createButton`, `fn createSVG`, `fn appendStyles` and `fn appendInlineStyles`.
- **Translating.** `fn t`.

Each listening helper takes two forms: a string for one of the player's own events, a plugin class for another plugin's.
`this.lifecycle.observe(observer)` puts a `cls ResizeObserver`, or any object with a `disconnect()`, under the same cleanup.

`emit(event, data)` is fire-and-forget.
`dispatchBefore(name, data)` lets a listener mutate, cancel or delay the action first.

`throw(payload)` surfaces the error and aborts the flow.
`report(payload)` surfaces it and returns, at `str warning` severity unless the payload says otherwise.

`fetch(url, options?)` runs the player's own auth pipeline.
`resolveUrl(url, category?)` covers the URLs you cannot attach a header to.
`mount(name)` claims a `<div>` on the player container.

The raw equivalent of any of these leaks something past teardown, or drops a contract the helper carries.
`ts this.player.on` skips both the scoping and the auto-removal.
A bare `fn setTimeout` outlives the plugin, a bare `fn fetch` sends no credentials, and a bare `ts throw` reaches nobody's error handler.

The `@nomercy-entertainment/eslint-plugin-player` rules flag each of those as you write them.

`dispose()` is where a plugin releases what the helpers cannot track, such as a third-party library instance.
Leave it out and that instance stays alive after the plugin is gone.

**The helpers' own cleanup runs after your `dispose()` returns.**
Inside `dispose()` the listeners are still subscribed, the timers are still armed, and the mount node is still on the page.

## What a plugin declares about itself

Statics are how a plugin describes itself to the registration pipeline, before any of its code has run.

Three describe identity: `id`, `description`, and a `version` that defaults to `str 0.0.0`.

Three form the registration contract and are settled before the plugin is constructed: `requires`, `replaces` and `minCoreVersion`.
A missing dependency, an unmet version floor or a duplicate id throws at that point rather than failing quietly later.

`priority` defaults to `0` and is read later, by `enabledPlugins()`.

Three more are behavior expressed as data instead of code.
`translations` are merged into the player's bundle and removed again on teardown.
`onError` maps an error code to a recovery action, and `advisories` declares that a given method is risky in a given phase, which the player then reports for you.

## Disabled is not removed

A plugin is enabled from the moment it is constructed.

`disable(reason?)` stops the behavior without unloading anything.
Listeners stay subscribed, timers keep their handles, and mounted DOM stays on the page.
This is also what the runtime does to a plugin whose declared dependency failed to install.

`enable()` starts the behavior again, and there is nothing to re-wire.
Both calls are idempotent, and both announce themselves on `str plugin:enabled` and `str plugin:disabled`.

Because nothing is unsubscribed, a disabled plugin's handlers still run.
Guarding them is the plugin author's job:

{/* partial */}
```ts
override use(): void {
  this.on('time', () => {
    if (!this.enabled())
      return;
    this.redraw();
  });
}
```

**Removal is the one that actually releases.**
`removePlugin(PluginClass)` runs the plugin's `dispose()`, drops everything its helpers registered, unmerges the translations it declared, and emits `str plugin:disposed`.

Plugins that declared a dependency on it are removed first.
Pass `{ cascade: false }` to refuse instead, which throws `str core:plugin/has-dependents` and names them.

A removed plugin is gone. Getting it back means calling `fn addPlugin` again.

`plugins()` lists every registered plugin in registration order.
`enabledPlugins()` lists only the enabled ones, ordered by `priority`, highest first.

## Reading and changing a plugin from outside

`state()` returns a snapshot: the id, the version, whether it is enabled, its options, and a `key runtime` object.

That last one is empty until the plugin fills it, by overriding `getRuntimeState()`.

`options()` returns a frozen copy of the current options.
`options(partial)` merges into them and announces the change on `str plugin:opts:changed`, which is where a plugin reacts to being reconfigured while it runs.
