# Plugins

A plugin is a class that extends `Plugin`. That is the whole of the definition.

You never construct one yourself.
You hand the class to the player, and the runtime instantiates it, wires it, and tears it down again.

```ts
player.addPlugin(PlayCounterPlugin, { everyNPlays: 2 });
```

The class is the handle for everything afterwards, which is why the class and not an id is what you pass.

`getPlugin(PluginClass)` hands back the live instance typed as that class.
`static requires` names other plugin classes rather than their ids.
`on(PluginClass, 'event', fn)` types the payload from the class you name.

`addPlugin` returns the player, so registrations chain.
The `plugins` array in `setup()` is the same call under another spelling, with identical validation and timing.

## The id is a namespace, not a label

`static id` is the one field every plugin must set, and nearly every other behavior on this page derives from it.

A plugin with `id = 'play-counter'` gets a logger prefixed `[nmplayer][play-counter]`, storage keys prefixed `nmplayer-play-counter-`, and a mount node classed `nmplayer-play-counter-<name>`.
Its events go out as `plugin:play-counter:<event>`, its translation keys resolve under `plugin.play-counter.*`, and every error it raises is stamped with that id.

Two plugins can therefore do the same thing without ever colliding, and none of them has to remember to prefix anything.

## `use()` is the hook you write

`use()` is the one method a plugin author overrides to do setup work.

The runtime calls it once, after it has wired the instance with the player, your options, the scoped logger and the scoped storage.
It may return a promise, and the runtime awaits it before the player reports itself ready.

The default body is empty, so a plugin that only declares statics needs no `use()` at all.

Subscribing, building DOM, fetching, opening a socket: all of it starts here.

**A plugin that throws from `use()` is torn back down rather than left half-installed.**
The player keeps going without it, and announces the loss on `plugin:failed`.

`this.player` is the player itself, so its methods are yours to call normally.
`this.opts` is exactly the object you passed to `addPlugin`, and `undefined` when you passed none.

## Helpers, so nothing outlives the plugin

The base class carries a helper for every global a plugin would otherwise reach for.

Every helper that opens something registers the matching cleanup as you call it, so teardown releases the lot and the plugin holds no handles of its own.

- **Listening.** `on`, `once`, `off` and `hasListeners`, in two forms: a string for the player's own events, a plugin class for another plugin's.
- **Timers and observers.** `listen`, `timeout`, `interval`, `frame` and `abortable`. `this.lifecycle.observe(observer)` does the same for a `ResizeObserver` or any object with `disconnect()`.
- **Speaking.** `emit(event, data)` for fire-and-forget, and `dispatchBefore(name, data)` when listeners should be able to mutate, cancel or delay the action.
- **Failing.** `throw(payload)` surfaces the error and aborts the flow. `report(payload)` surfaces it and returns, defaulting to `warning` severity.
- **Network.** `fetch(url, options?)` runs the player's own auth pipeline and aborts on teardown. `websocket(url, opts?)` closes on teardown. `resolveUrl(url, category?)` covers the URLs you cannot attach a header to.
- **Building.** `mount(name)` claims a `<div>` on the player container and removes it again. `createElement`, `createButton`, `createSVG`, `appendStyles` and `appendInlineStyles` build the rest.
- **Translating.** `t(key, vars?)`, which looks the key up under the plugin's own namespace.

The raw equivalent of any of these leaks something past teardown, or drops a contract the helper carries.
`this.player.on` skips both the scoping and the auto-removal.
A bare `setTimeout` outlives the plugin, a bare `fetch` sends no credentials, and a bare `throw` reaches nobody's error handler.

The `@nomercy-entertainment/eslint-plugin-player` rules flag each of those as you write them.

Override `dispose()` only for something the helpers cannot already track, such as a third-party library instance.
Whatever they do track is released before your `dispose()` runs.

## What a plugin declares about itself

Statics are how a plugin describes itself to the registration pipeline, before any of its code has run.

Three describe identity: `id`, `description`, and a `version` that defaults to `'0.0.0'`.

Three form the registration contract and are settled before the plugin is constructed: `requires`, `replaces` and `minCoreVersion`.
A missing dependency, an unmet version floor or a duplicate id throws at that point rather than failing quietly later.

`priority` defaults to `0` and is read later, by `enabledPlugins()`.

Three more are behavior expressed as data instead of code.
`translations` are merged into the player's bundle and removed again on teardown.
`onError` maps an error code to a recovery action, and `advisories` declares that a given method is risky in a given phase, which the player then reports for you.

## Disabled is not removed

A plugin is enabled from the moment it is constructed.

`disable(reason?)` stops the behavior without unloading anything.
Listeners stay subscribed, timers keep their handles, and mounted DOM stays on the page.
This is also what the runtime does to a plugin whose declared dependency failed to install.

| State | Listeners, timers and DOM | Reached by |
| --- | --- | --- |
| Enabled | Live | `addPlugin`, then `enable()` |
| Disabled | Still live | `disable(reason?)` |
| Removed | Released | `removePlugin(PluginClass)` |

Because nothing is unsubscribed, a disabled plugin's handlers still run.
Guarding them is the plugin author's job:

{/* partial */}
```ts
override use(): void {
  this.on('time', () => {
    if (!this.enabled())
      return;
    this.redraw();
  });
}
```

Both calls are idempotent, and both announce themselves on `plugin:enabled` and `plugin:disabled`.

**Removal is the one that actually releases.**
`removePlugin(PluginClass)` runs the plugin's `dispose()`, drops everything its helpers registered, unmerges the translations it declared, and emits `plugin:disposed`.

Plugins that declared a dependency on it are removed first.
Pass `{ cascade: false }` to refuse instead, which throws `core:plugin/has-dependents` and names them.

A removed plugin is gone. Getting it back means calling `addPlugin` again.

`plugins()` lists every registered plugin in registration order.
`enabledPlugins()` lists only the enabled ones, ordered by `priority`, highest first.

## Reading and changing a plugin from outside

`state()` returns a snapshot: the id, the version, whether it is enabled, its options, and a `runtime` object.

That last one is empty until the plugin fills it, by overriding `getRuntimeState()`.

`options()` returns a frozen copy of the current options.
`options(partial)` merges into them and announces the change on `plugin:opts:changed`, which is where a plugin reacts to being reconfigured while it runs.
