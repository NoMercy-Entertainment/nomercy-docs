# The Event Bus

A player announces everything it does as an event.

All of it runs through one class, `cls EventEmitter`, and the player instance is one.
So `player.on(...)` is the whole subscription surface, with nothing to wire up first.

## Subscribing

```ts
player.on('play', () => showPauseButton());
```

`fn on` runs your handler on every emit of that name.
`fn once` runs it on the next emit and then removes it.
Remove one yourself with `fn off`:

```ts
player.off('play', showPauseButton);
```

Pass the same function reference you subscribed with.
That is also how a `fn once` handler is canceled before it has fired.

Registering one function twice for one event registers it once.
The second call is not a second subscription.

**`off(name)` with no handler drops every listener for that name.**

**`off('all')` with no handler drops every listener for every name.**
Disposal uses that second form, so reach for it only when you are finished with the player.

### What the types catch, and what they do not

A name from the player's event map hands your handler the right shape:

```ts
player.on('playlistReady', ({ length }) => {
  // length is a number here.
});
```

**A name that is not in the map still compiles.**
A bare string is a valid call, because a plugin's own `plugin:<id>:<event>` names have to be subscribable too.
So a misspelled name gives you a handler that never runs, rather than a build error.

The runtime covers part of that gap.
Subscribing to a name the bus knows will never fire logs a console warning naming the one to use instead.

## The firehose

```ts
player.on('all', (event, data) => console.log(event, data));
```

`str all` calls your handler for every emit, with the name first and the payload second.
That is the debugging hook.
Remove one with `off('all', fn)`.

Firehose listeners are held apart from named ones.
`hasListeners('all')` is false while one is registered, because it answers about named subscriptions only.

## What an emit guarantees

`hasListeners(name)` exists for a payload that costs something to build:

```ts
if (player.hasListeners('debug:frame'))
  player.emit('debug:frame', buildFrameReport());
```

Three things hold on every dispatch.

- Handlers run in subscription order, synchronously.
- The listener set is snapshotted first, so an `off()` inside a handler takes effect on the next emit rather than this one.
- A handler that throws is caught and logged, and the remaining handlers still run.

That last one is why one broken listener cannot stop the player telling everybody else what happened.

Whenever a name gains its first listener or loses its last, the bus emits `str listeners-changed` with `{ name, count }`.
It arrives on a microtask, not inside your `on()` call.

`cls EventEmitter` is exported on its own, so every mechanic above can be driven with no player around it.

## Canceling an action

An action the player is about to take announces itself first, on an event named `before` plus the action.
Eighteen events in the core map work this way, `beforePlay`, `beforeSeek` and `beforeLoad` among them.

A handler for one of those receives an event object rather than the payload:

```ts
player.on('beforeSeek', (event) => {
  if (isAdPlaying())
    event.preventDefault();
});
```

`preventDefault()` cancels the action.
The player skips the work and the event that would have followed it, and emits `<action>Prevented` in its place:

```ts
player.on('seekPrevented', ({ reason }) => console.log(reason));
```

`event.data` is the payload, and it is writable.
The player reads it back, so a handler can change what the action does rather than stopping it:

```ts
player.on('beforeSeek', (event) => {
  event.data.time = clampToChapter(event.data.time);
});
```

`stopImmediatePropagation()` skips the handlers subscribed after yours.
It cancels nothing on its own, so combine it with `preventDefault()` when you mean both.

## Holding an action open

`delay(promise)` makes the player wait before it acts:

```ts
player.on('beforePlay', (event) => {
  event.delay(refreshCredentials());
});
```

Several handlers may delay one action, and their promises are awaited together.

The wait is capped, and the cap is 10000 ms.
Set your own with `key beforeEventTimeoutMs` in the setup config.

A delayed promise that rejects cancels the action.
So does running out of time.

`key reason` on the `<action>Prevented` payload says which of four cases you are in.

| `key reason` | The action stopped because |
| --- | --- |
| `str listener-prevented` | A handler called `preventDefault()`. |
| `str delay-rejected` | A delayed promise rejected. The rejection arrives beside it as `key cause`. |
| `str delay-timeout` | The delays outlasted the cap. |
| `str backend-refused` | The browser or the backend declined the call itself. |

`str backend-refused` is the one no handler causes.
A browser blocking autoplay is the case you will actually meet.

**Order decides whether a delay is honored.**
Every handler runs to the end before any promise is awaited.
So a handler that stops propagation silences a later handler's `delay()`.

The action then goes ahead unwaited.

`player.dispatching()` returns the names being dispatched right now, innermost last.
Reach for it when a handler needs to know which chain it is inside.
