# Core: Lifecycle & Setup

`setup()` is the one strict step every player library composed from the kit shares: call it once, and a fixed pipeline runs before anything else can happen.

## The pipeline

`setup(config)` snapshots your config and wires the cross-cutting policies: visibility, network, wake lock, metrics, preload and transition orchestration.

Then it runs an ordered async sequence.

```text
setupStart -> configResolved
  -> pluginsRegistering -> pluginsRegistered
  -> streamsReady -> authReady
  -> playlistResolving   (only when the playlist is a URL)
  -> playlistReady -> mediaReady -> ready
```

Each stage emits its own name on success, or a matching `<stage>Error` on failure. A failure short-circuits the rest and rejects `ready()`.

Playlist resolution is the exception. It never throws. A fetch or parse failure emits `playlistError`, and the pipeline still reaches `mediaReady` and `ready` with an empty queue.

`ready()` returns a promise that resolves once the pipeline reaches `ready`, or rejects if a stage failed or `dispose()` ran first. It's memoised, so calling it from multiple places in your player library returns the same promise rather than re-running anything.

Call `setup()` a second time on the same instance and it throws `core:lifecycle/already-setup`.

That guard is checked first and stays tripped across a `dispose()` in between. Reuse after teardown needs a fresh instance, not a second `setup()`.

The narrower `core:player/disposed` guard fires only when `setup()` runs for the first time on an instance that was disposed before `setup()` ever ran.

There is exactly one way in.

## The phase machine

Underneath the pipeline sits a closed set of phases.

```text
idle -> setup -> ready
     -> loading / starting / playing / paused
      / buffering / seeking / ended / stopped
     -> disposing -> disposed
```

`phase()` reads the current one. The `phase` event fires `{ from, to }` on every transition.

So a UI layer or a plugin drives an overlay off phase changes alone, instead of piecing state together from a dozen flags.

Two guard methods sit on top of the phase machine, and every transport method (`play`, `pause`, `stop`, `next`, `previous`, and the rest) calls the first one before doing anything else:

- `_assertReady()`: throws `core:player/not-ready` before `setup()` has run, or `core:player/disposed` after `dispose()`.
- `setupState()`: a coarser read for UI gating, one of `SetupState.NOT_SETUP`, `SETTING_UP`, `READY`, `DISPOSED`.

## Composing a player-library author sees

Building a player library on the kit means two things. Your constructor calls `initPlayerCoreState()`, and `composeMixins` stamps `lifecycleMethods` onto your prototype along with the rest of `playerCoreMethods`.

From there, `setup()`, `ready()`, `dispose()` and the phase machine work as described above, with or without a media backend attached.

## Disposal

`dispose()` is idempotent. A second call does nothing.

It dispatches `beforeDispose` first, and a listener can call `preventDefault()` to keep the player alive. `disposePrevented` fires instead.

Otherwise it drains every cleanup callback the `setup()` wiring registered, in order, then emits `dispose` and moves to `disposed`.

A handler watching that transition sees a consistent final state, not a half-torn-down one.
