# Lifecycle

Call `fn setup` once after you compose your class.
It returns right away, before the player is usable.
Await `fn ready` before you read the queue or start playback.

## Start setup

```ts
player.setup(config);
```

`fn setup` takes a `cls BasePlayerConfig` object.
It snapshots that object onto `key options` and seeds internal slots from it.
It adds the `str nomercyplayer` class on the container.

It emits `str beforeSetup` and moves into the `str setup` phase.
Then it starts the async pipeline that ends at `str ready`.

A second `fn setup` throws `str core:lifecycle/already-setup`, including after `fn dispose`.
Dispose does not make this instance accept setup again.
Build a new instance when you need another player.

## Wait until ready

```ts
await player.ready();
```

`fn ready` resolves when the pipeline reaches the `str ready` phase.
If the player is already ready, it resolves at once.
If the player is disposing or disposed, it rejects with `str core:player/disposed`.

Repeated calls share the same promise.
When a plugin is still registering after setup, `fn ready` waits for that too.

Handle a rejected `fn ready` like any other failed promise.
A stage that throws emits that stage's error event and either `str error` or `str fatal`.
Then it rejects `fn ready`, so later stages do not run.

## The setup sequence

Stages run in a fixed order.
Each successful stage emits an event with the same name.

```
setupStart → configResolved → pluginsRegistering → pluginsRegistered
  → streamsReady → authReady → playlistReady → mediaReady → ready
```

Hang your own work off a stage event when you need that point, not a delay.

These stages are the ones you usually wait on.

| Stage | Settled when it fires |
| --- | --- |
| `str configResolved` | `key options` holds the config snapshot. |
| `str pluginsRegistered` | Plugins queued for setup have finished registering. |
| `str streamsReady` | Built-in stream factories are registered when missing. |
| `str authReady` | The auth stage has passed in the sequence. |
| `str playlistReady` | The queue is seeded, or `key length` is `0`. |

`str mediaReady` fires when that stage runs, and its work body is empty.

`str setupStart` carries the container.
A playlist URL also emits `str playlistResolving` with that URL between `str authReady` and `str playlistReady`.

A playlist fetch failure emits `str playlistError` and still emits `str playlistReady` with `length: 0`.
The pipeline continues to `str ready`.

Pass `key plugins` on the config, or register before `fn setup`, so they drain during `str pluginsRegistering`.
Each registration is bounded by `key pluginInitTimeoutMs`, which defaults to `30000`.

## Check where you are

`fn phase` returns the fine-grained phase string, such as `str idle`, `str setup`, or `str ready`.
`fn setupState` returns a coarser `cls SetupState`: `str not-setup`, `str setup`, `str ready`, or `str disposed`.

Use `fn setupState` when you only need to know whether the player is usable yet.

## Viewer activity

After `fn setup`, the player watches the container for pointer, touch, and key input.
It emits `str activity` with `key active` set to `true` or `false`.

```ts
player.on('activity', ({ active }) => showControls(active));
player.bumpActivity();
```

Controls start visible because setup bumps activity once.
While playing, inactivity after `key inactivityMs` (default `4000`) emits `active: false`.
Leaving the container while playing hides the controls at once.

Hide runs only while `fn playState` is `str playing`.
Any other play state leaves the controls up.
`fn bumpActivity` marks the viewer active and re-arms that countdown.
Call it after input the container cannot see, such as a remote command.

`fn activityTracking` with no argument returns whether the built-in tracker owns `str activity`.
Pass `false` when your UI takes over emission; the countdown clears and the listeners stand down.
Set `key inactivityMs` to `0` to skip wiring the built-in tracker at setup.

## Tear down

```ts
await player.dispose();
```

`fn dispose` is safe to call twice; the second call does nothing.

It first dispatches `str beforeDispose`.
A listener may call `fn preventDefault` to cancel.
When a listener cancels, the player emits `str disposePrevented` and stays fully alive.

Otherwise plugins dispose in reverse registration order.
Then the cleanup callbacks from setup run.
`str dispose` fires next.

The phase becomes `str disposed`, and every listener is removed.

If `fn ready` had not resolved yet, dispose rejects it with `str core:player/disposed`.
The instance is dead afterward; construct a new player for a fresh setup.
