# Lifecycle

`setup()` returns straight away. The player is not usable yet.

What happens between that return and a usable player is a fixed sequence of stages, each of which announces itself.

The sequence is what tells you where your own code belongs.
It is also why a call that works in one place returns nothing in another.

## The sequence

Nine stages, always in this order:

```
setupStart → configResolved → pluginsRegistering → pluginsRegistered
  → streamsReady → authReady → playlistReady → mediaReady → ready
```

Each stage emits an event named after itself. Subscribing to one is how you hang your own work off a point in the sequence rather than guessing at a delay:

```ts
// The queue is populated here, which is the earliest point a
// "restore where they left off" call has anything to act on.
player.on('playlistReady', ({ length }) => {
  if (length > 0)
    restoreLastPosition(player);
});
```

One extra event appears only when the playlist has to be fetched.
A config that hands the player a URL instead of an array emits `playlistResolving` with that URL, between `authReady` and `playlistReady`.

## What each stage settles

The names describe what has finished, not what is starting.

| Stage | True once it has fired |
| --- | --- |
| `configResolved` | `player.options` is final. Your config object has been taken as given. |
| `pluginsRegistered` | Every plugin has constructed and its `use()` has returned. |
| `streamsReady` | The stream factories are registered, so a URL can be matched. |
| `authReady` | Credentials are in place, so a media request can be signed. |
| `playlistReady` | The queue is populated. The payload carries `length`. |

Two of the nine are the wrong hook to reach for, and both look right by their name.

**By the time `setupStart` fires, the config is normalized, state is seeded and the adapters are wired.**
Some fields have been read by then and some have not, so an edit there lands for `playlist` and is ignored for whatever was already consumed.
Pass config to `setup()` and you never have to know which is which.

**`mediaReady` fires twice.**
The stage of that name has an empty body and fires whether or not media loaded.

The load path emits it again once the backend really holds an item.

Listen for it after `ready()` resolves and you get that second one.

## Waiting for it

```ts
await player.ready();
```

**Past that line every method is safe to call.** Restoring a saved position, selecting a track, reading the queue: all of it belongs after `ready()` resolves and none of it before.

Calling `ready()` on a player that has already reached the ready phase resolves immediately, so it is safe in a code path that may run twice.

**A stage that throws stops the sequence.** It emits two events, a `<stage>Error` naming the stage and a general `error`, and then rethrows. No later stage runs, `ready` never fires, and the promise `ready()` handed you rejects.

So `ready()` is where a setup failure surfaces, and it needs handling like any other rejection:

```ts
try {
  await player.ready();
}
catch (error) {
  showPlaybackUnavailable(error);
}
```

A player left in that state has not been disposed. Call `dispose()` yourself before building another one.

**One failure deliberately does not stop the run, and it is the one you will actually meet.** A playlist that cannot be fetched emits `playlistReady` with `length: 0` and the sequence carries on to `ready`. A queue that is unexpectedly empty after `ready()` resolves is that failure, not a bug in your own code.

## Where a plugin fits

Plugins queued before `setup()` are constructed during `pluginsRegistering`, the third stage.

**Registering later still works, and the difference is when.**
A plugin added after the player is ready is registered on the spot rather than as part of the sequence, so it comes up against a live player instead of a half-built one.

Register before `setup()` when the plugin needs to watch the setup stages happen, which is what a plugin drawing an interface wants.

Each plugin goes through the same four steps, in order:

1. **Construct.** The class is instantiated with no arguments.
2. **Initialize.** The runtime hands it the player, its options, and the registry that will dispose whatever it opens.
3. **Merge translations.** Any translations declared on the class join the player's bundle.
4. **Call `use()`.** `use()` is the one method a plugin author writes to do setup work, and the runtime awaits it here.

**`use()` is bounded by a timeout, and the default is 30 seconds.** A plugin whose `use()` never resolves would otherwise hold the whole sequence open, so the timeout is what guarantees `ready` still arrives.

Raise or lower it on the player config, in milliseconds:

{/* partial */}
```ts
player.setup({
  pluginInitTimeoutMs: 5_000,
  ...
});
```

A plugin that throws, or times out, is torn back down rather than left half-installed. Anything that declared a dependency on it is disabled, and the player itself keeps going.

That failure is announced, so your own code can react to a missing capability rather than discovering it later:

```ts
player.on('plugin:failed', ({ id, error }) => {
  console.warn(`${id} did not install`, error);
});
```

## Disposal runs the other way

```ts
await player.dispose();
```

**Nothing is still listening**, and the video element is gone if the player created it.

A `<video>` you put in the container yourself is left in place, and the `nomercyplayer` class stays on the container either way.
The instance is dead afterwards, so a later player means constructing a new one.

What happens in between is worth knowing, because you can stop it.

`beforeDispose` fires first, and a listener can stop it by calling `preventDefault()` on the event it receives:

```ts
player.on('beforeDispose', (event) => {
  if (hasUnsavedProgress())
    event.preventDefault();
});
```

Nothing is torn down when one does, so holding a player open until you have flushed state is a legitimate use of it.

A listener that needs to finish asynchronous work first calls `event.delay(promise)` instead. Disposal waits for it, and a promise that rejects prevents the disposal rather than letting it proceed half-done.

Otherwise every plugin is disposed in reverse registration order, and then the kit drops every listener it holds. The backend and the element are torn down after that, by the player library wrapped around the kit.
