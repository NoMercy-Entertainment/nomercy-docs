# Errors

A failure reaches you as an event, not as a thrown exception you have to catch around every call.

The severity decides which event. There are four, they are the complete set, and the event is named after the severity:

```ts
player.on('error', ({ error }) => report(error.code, error.context));
player.on('fatal', ({ error }) => showPlaybackFailed(error.suggestion ?? error.message));
```

## Which one you must handle

Two of the four change what a person sees. The other two are for your logs.

| Severity | Means | What it asks of you |
| --- | --- | --- |
| `fatal` | Unrecoverable. The player is shutting down. | Tell the viewer. Nothing will recover on its own. |
| `error` | Recoverable, such as a sidecar that failed to load. | Decide whether the feature it broke matters here. |
| `warning` | Observability only. | Log it. |
| `info` | Observability only. | Log it. |

**Subscribing to `error` does not give you `fatal` as well.** They are separate channels, so a handler on one hears nothing from the other. Wire both, and treat `fatal` as the one that has to reach the screen.

## What every failure carries

The same shape arrives on all four channels.

```ts
{
  code: string;                          // stable, and what a bug report is searched by
  severity: 'fatal' | 'error' | 'warning' | 'info';
  scope: ErrorScope;                     // where it came from
  message: string;
  cause?: unknown;                       // the original failure, when there was one
  context?: Record<string, unknown>;     // the values involved
  suggestion?: string;                   // present on some codes, not all
}
```

**Log the `code`, never the `message`.** The code is stable and the message is not, so a code is what makes two reports of the same failure look like the same failure.

`scope` says which part raised it. It is a discriminated union rather than a string, so branching on `scope.kind` routes a failure without matching on code prefixes.

`{ kind: 'core' }` and `{ kind: 'network' }` carry nothing else. `{ kind: 'plugin', id }` names the plugin. The backend, stream and cue scopes each name the implementation involved.

`suggestion` is populated for some codes and absent for others, so `error.suggestion ?? error.message` is the pattern that always has something to show.

## Failures during setup arrive twice

A setup stage that fails emits two events: one named after the stage, and one named after the severity.

That looks like duplication and it is deliberate.

The stage event tells you *where* the run stopped, which is what a diagnostic needs.

The severity event tells you *how bad it is*. It arrives on the same channel as every other failure, so one handler covers them all.

Listening to both means seeing one failure twice. Pick the one that suits the job.
