# Errors

Most failures reach you on one of four severity channels, each named after its severity:

```ts
player.on('error', ({ error }) => report(error.code, error.context));
player.on('fatal', ({ error }) => showPlaybackFailed(error.suggestion ?? error.message));
```

Some calls throw instead of emitting.
`ready()` rejects when a setup stage fails.
`load()` throws `core:media/missing-url` when the item you passed has no `url`.

**Four failures never reach a severity channel.**
Each has an event of its own: `plugin:failed`, `playlistError`, `auth:failed` and `preloadError`.
A handler on `error` hears none of the four, so these are wired separately.

## Which one you must handle

Two of the four change what a person sees. The other two are for your logs.

| Severity | Means | What it asks of you |
| --- | --- | --- |
| `fatal` | Unrecoverable. The play state flips to `ERROR`. | Tell the viewer. The player does nothing further about it. |
| `error` | Recoverable, such as a playlist that could not be fetched. | Decide whether the feature it broke matters here. |
| `warning` | Observability only. | Log it. |
| `info` | Observability only. | Log it. |

**Subscribing to `error` does not give you `fatal` as well.** They are separate channels, so a handler on one hears nothing from the other. Wire both, and treat `fatal` as the one that has to reach the screen.

## What every failure carries

The same shape arrives on all four channels.

{/* partial */}
```ts
{
  code: string;                          // the identifier a bug report is searched by
  severity: 'fatal' | 'error' | 'warning' | 'info';
  scope: ErrorScope;                     // where it came from
  message: string;
  cause?: unknown;                       // the original failure, when there was one
  context?: Record<string, unknown>;     // the values involved
  suggestion?: string;                   // present on some codes, not all
}
```

**Log the `code`, never the `message`.**
The message is free text written at the raise site.
The code is a fixed identifier, which is what makes two reports of one failure look alike.

`scope` says which part raised it. It is a discriminated union rather than a string, so branching on `scope.kind` routes a failure without matching on code prefixes.

There are seven kinds.

- `core`, `network` and `auth` carry nothing else.
- `plugin`, `backend`, `stream` and `cue` each carry an `id` naming what raised it.

`suggestion` is populated for some codes and absent for others, so `error.suggestion ?? error.message` is the pattern that always has something to show.

## Failures during setup arrive twice

Setup runs as a sequence of named stages, which [Lifecycle](/nomercy-player-core/tour/lifecycle) walks through.
Most of them announce a failure twice.

The first event is the stage's name with `Error` on the end, so `authReady` fails as `authReadyError`.
The bare stage name is the success event, so a listener on `authReady` hears nothing about the failure.

The second is `error`.
**A stage failure always arrives there, and never on `fatal`.**

The stage event tells you where the run stopped.
The `error` event is the one handler that catches a setup failure alongside every other failure of that severity.

`playlistReady` is the one stage that does not do this.
It announces a failure on `playlistError` alone, which is why that name is in the list of four above.

Listening to both means seeing one failure twice. Pick the one that suits the job.
