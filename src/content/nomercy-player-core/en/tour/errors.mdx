# Errors

Import the error classes from `@nomercy-entertainment/nomercy-player-core`.
A typed failure is a `cls PlayerError`, so you can catch by class, by `key code`, or by both.
That routes a network fault away from a lifecycle fault without parsing free text.

## When a failure reaches you

Some call sites throw a `cls PlayerError` subclass you catch with `try` / `catch`.
Other failures reach listeners as a `PlayerErrorEvent` on `str fatal`, `str error`, `str warning`, or `str info`.
The event wraps the same error object, so one `instanceof` branch works for both paths.

On the event, `fn markHandled`, `fn stopImmediatePropagation`, and `fn preventDefault` set flags.
Read them back with `fn isHandled`, `fn isPropagationStopped`, and `fn isDefaultPrevented`.
Listeners on those four channels still all run, because that emit does not read the flags.

## What every error carries

`cls PlayerError` extends `Error`.
Severity defaults to `str error` when the raise site omits it.
Match on `key code`, not on `key message`, because the code is the stable id.

These fields are what you read after a catch or on an event.

`key code` is the stable string id you match and log.
`key severity` is `str fatal`, `str error`, `str warning`, or `str info`.
`key scope` names where it came from.

`key context` holds optional diagnostics, often with `key httpStatus`.
`key suggestion` is an optional hint for your UI.
`key cause` is an optional underlying value.

`fn isHttp` is true when `key context.httpStatus` falls in that HTTP century.
Use `error.suggestion ?? error.message` when you need something to show.
An optional numeric `key id` may sit beside the string code for compact logs.

`key scope` is a discriminated union, so branch on `key scope.kind` without matching code prefixes.
Kinds without an id are `str core`, `str network`, and `str auth`.
Kinds with an id are `str plugin`, `str backend`, `str stream`, and `str cue`.

## Subclasses you catch

Pick the narrowest `instanceof` that fits.
`cls AuthError` extends `cls NetworkError`, so a network catch also sees auth failures.

These are the classes you reach for first:

| Class | Catch when |
| --- | --- |
| `cls PlayerError` | Any typed player failure |
| `cls NetworkError` | Transport failure, or HTTP status in context |
| `cls AuthError` | HTTP 401 or 403 |
| `cls StateError` | Method called in the wrong lifecycle phase |
| `cls MediaFormatError` | Browser rejects the codec or container |

A 401 may be refreshed before `cls AuthError` is raised.
A 403 raises it at once.

`cls PluginError` covers plugin registration or a plugin throw.
`cls DrmError`, `cls StreamError`, `cls ResourceError`, `cls BrowserPolicyError`, and `cls NotImplementedError` cover the remaining cases.
Factories such as `fn stateError`, `fn pluginError`, `fn mediaFormatError`, `fn resourceError`, and `fn browserPolicyError` stamp scope and a default severity for you.

String codes follow patterns like `str core:state/<reason>` and `str core:media/<reason>`.
The full code list and default retry policy belong on the [errors reference](/nomercy-player-core/reference/errors).

## Codes and severity helpers

String codes such as `str core:auth/forbidden` are what application code matches on.
Numeric ids from `fn makeCode` are optional helpers for compact logs.
`fn parseCode` and `fn formatCode` round-trip that eight-digit form.
`key SEVERITY` and `key SEVERITY_LEVEL` map the four severity strings to digits 1 through 4.
