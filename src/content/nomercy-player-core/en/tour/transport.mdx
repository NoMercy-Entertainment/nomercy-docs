# Transport

Every transport call runs the same three steps.

It announces the intent, gives your listeners a chance to stop it, and only then changes state and calls the backend.

That shape is what makes the events predictable, and it is what lets a plugin veto an action instead of undoing it afterwards.

## What each call announces

| Call | Announces first | Emits when it runs |
| --- | --- | --- |
| `play()` | `beforePlay` | `play` |
| `pause()` | `beforePause` | `pause` |
| `stop()` | `beforeStop` | `stop` |
| `next()` | `beforeNext` | `next`, or `queue:exhausted` |
| `previous()` | `beforePrevious` | `previous` |

`togglePlayback()` announces nothing of its own.
It reads the current play state and calls `pause()` when it is playing, `play()` otherwise, so one of the pairs above fires instead.

`rewind()`, `forward()` and `restart()` announce on `beforeSeek`, then emit `seek` and `seeked`.

## Stopping one before it happens

A `before*` listener receives an event object rather than the payload.
Calling `preventDefault()` on it cancels the action:

```ts
player.on('beforePlay', (event) => {
  if (event.data.source === 'remote')
    event.preventDefault();
});
```

**A cancelled action changes nothing.** No state moves, the plain event never fires, and the backend is never called.

What fires instead is `<action>Prevented`, carrying a `reason` and, when there was one, a `cause`:

```ts
player.on('playPrevented', ({ reason }) => {
  console.log('play blocked:', reason);
});
```

`reason` is `listener-prevented` when a listener cancelled it.

## `play` is not proof that playback started

`play()` sets the play state and emits `play` before it asks the backend to play.

**When the backend refuses, the `play` event has already fired.**
The refusal you will actually meet is a browser declining autoplay without a gesture.

The player then rolls the state back to paused, emits `playPrevented` with reason `backend-refused`, and rethrows.

So an unawaited `play()` becomes an unhandled rejection, and it needs catching even though the event already told you:

```ts
player.on('playPrevented', ({ reason }) => {
  if (reason === 'backend-refused')
    showTapToPlay();
});

try {
  await player.play();
}
catch {
  // Already reported through playPrevented.
}
```

`pause()` and `stop()` cannot fail this way, because neither awaits its backend call.

## Seeking by a delta

`rewind(seconds)` and `forward(seconds)` move relative to the current position, and both default to 5.

`rewind()` clamps at 0, so rewinding past the start lands on the start.
`forward()` has no upper clamp, and a backend that cannot seek past the end snaps there itself.

`restart()` seeks to 0 and then plays.
A prevented seek skips the play as well, because restart is one intent rather than a seek followed by a play.

**These three tell `beforeSeek` the delta, not the destination.**
A `forward(10)` listener sees `time: 10`, a `rewind(10)` listener sees `-10`, and `restart()` sends `0`.

The `seek` and `seeked` events that follow carry the absolute target instead.

**Rewriting `event.data.time` in a `beforeSeek` listener does not move any of the three.**
They work out their target before the dispatch and keep it, and only `source` is read back off the event.

Seeking to a position you name belongs to [Time](/nomercy-player-core/tour/time).

## The seeking phase

A seek moves the player into the `seeking` phase and back to the phase it was in.

**That round trip only happens from `playing`, `paused` or `starting`.**
A seek before playback has started emits no phase change at all, which is what keeps a restored position from flashing a seeking state through your interface.

A prevented seek changes no phase either.

## Moving through the queue

`next()` reads the repeat mode, set with `repeatState()`, and does one of three things.

- `'one'` reloads the current item. The queue cursor does not move.
- `'all'` wraps to the first item once there is no next one.
- `'off'` emits `queue:exhausted` once there is no next one.

An empty queue emits `queue:exhausted` under all three.

`previous()` at the start of the queue does nothing, and says nothing.
Going back past the first item is a common gesture rather than a failure worth announcing.

Both move the queue cursor before they switch the media, so a title, a poster and a playlist highlight update while the incoming item is still loading.

**Awaiting `next()` means the item loaded, not that it is playing.**
Playback is started without being awaited, so a refusal there emits `playPrevented` and leaves the `next()` promise resolved.

A load that fails is the other way round: `next()` does await the load, so that failure rejects.

## Attributing an action

Every call on this page takes an options object with a `source` on it.

Whatever you put there is stamped onto the event that follows, and nothing fills one in when you leave it out.

```ts
player.on('play', ({ source }) => {
  if (source !== 'remote')
    broadcastToOtherDevices();
});

await player.play({ source: 'remote' });
```

That is what lets a plugin syncing playback across devices tell its own echo apart from a real press.

A `before*` listener can rewrite `event.data` too, and the plain event carries what the listener left behind.
`seek` carries a source as well. `seeked` does not.

## Before setup and after disposal

Every method on this page checks the player is usable before anything else.

Called before `setup()` it throws `core:player/not-ready`, and after `dispose()` it throws `core:player/disposed`.

Neither is preventable and neither emits, because the check runs ahead of the dispatch.
