Core ships one thing and only one: the engine, with no chrome on it. An
application that wants controls takes the video or music package, whose drop-in
view is a player. An application that has already drawn its own takes this and
gets the state machine, the event bus, the queue and the plugin runtime with
nothing on top.

```kotlin
dependencies {
    implementation("tv.nomercy:nomercy-player-core-kmp:2.0.0-rc.1")
}
```

```kotlin
val player = ComposedPlayer(backend)
player.setup()
player.queue(items)
player.play()
```

Everything the reference lists is on that object. What it announces reaches
anything subscribed, which is how a chrome, a notification and a cast session
stay in agreement without knowing about each other.

## The testing kit

The stand-ins ship as their own coordinate, so a consumer testing their own
integration writes none of their own.

```kotlin
commonTest.dependencies {
    implementation("tv.nomercy:nomercy-player-core-kmp-testing:2.0.0-rc.1")
}
```

It carries `FakeMediaBackend`, a `FakePlayer` with a real event bus and a real
plugin registry, fakes for storage, sockets and HTTP, and `testPlugin`, which
registers a plugin, hands it to you, tears it down and asserts the bus came back
to where it started. Every test written through it is also a leak test at no
cost to the author.

## The debug view

`PlayerInspector` records the firehose into a bounded buffer, and the overlay
renders it over whatever is playing.

```kotlin
val inspector = remember(player) { PlayerInspector(player) }

PlayerInspectorOverlay(inspector, Modifier.align(Alignment.TopEnd))
```

It answers what a breakpoint cannot: what happened just before the thing that
went wrong. The Compose overlay is in `nomercy-player-core-kmp-compose` and the
SwiftUI one in the `NoMercyPlayerDevTools` product, separate from the engine so
a debug view has to be asked for by name rather than arriving with it.
