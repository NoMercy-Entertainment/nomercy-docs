# Errors

A failed request answers with a problem document: the standard `application/problem+json` shape, plus the trace id for that request.

```json {{ title: 'A rejected request' }}
{
  "type": "/docs/errors/forbidden",
  "title": "Unauthorized.",
  "detail": "You do not have permission to manage libraries",
  "instance": "/api/v1/dashboard/libraries",
  "status": 403,
  "traceId": "0HN7GK3P1QK2M:00000003"
}
```

::properties

::property {{ name: 'type', type: 'string' }}

An identifier for the kind of failure. Stable, so it is safe to branch on.

::property {{ name: 'title', type: 'string' }}

The category, translated to the caller's language.

::property {{ name: 'detail', type: 'string' }}

What went wrong in this particular request. Read this one first.

::property {{ name: 'instance', type: 'string' }}

The path that was called.

::property {{ name: 'status', type: 'integer' }}

The HTTP status, repeated in the body.

::property {{ name: 'traceId', type: 'string' }}

Identifies this request in the server log. Quote it when reporting a problem.

::

## The statuses you will meet

| Status | Means |
|--------|-------|
| 400 | The request was malformed |
| 401 | No token, an invalid token, or an account this server does not know |
| 403 | Authenticated, but without the permission this endpoint needs |
| 404 | No such item, or none you may see |
| 409 | The change conflicts with the current state |
| 422 | The request was understood but the values will not do |
| 429 | Too many requests |
| 500 | The server failed |
| 503 | The server is not ready to answer yet |

## Telling 401 and 403 apart

This pair is worth getting right, because the fix differs.

**401** means the server did not accept the token. Either it is missing or expired, or the account behind it is not a user on this server. A token for a different NoMercy server lands here.

**403** means the token was fine and the account is real, but it lacks the permission. Granting the permission is a change the server owner makes in the dashboard.

## Finding the request in the log

Every problem document carries `traceId`, and the same id is written into the server log. Search for it there to see what the server was doing.

Log locations are listed in [Logs](/nomercy-media-server/troubleshooting/logs).
