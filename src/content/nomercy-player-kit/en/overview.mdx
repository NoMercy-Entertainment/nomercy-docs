# What is the NoMercy Player Core

Underneath, the video player and the music player are mostly the same machine.
A queue is a queue, auth is auth, and a plugin system does not care whether it is driving a film or an album.
`nomercy-player-core` is that shared machine pulled into its own package, so the two players do not each carry their own copy of it.
It is headless and you never run it directly, the library packages bring it along as a peer dependency.
What lives here is everything generic: the queue, the auth pipeline, the plugin system, the typed event bus, i18n, storage, and the adapter ports you swap when a default does not fit your platform.
Keeping it in one place means a fix lands in both players at once, and it keeps each player small enough to focus on the genuinely hard parts of its own domain.

The core owns:

- The mixin-composed prototype that every player instance is built from
- The adapter port contracts (storage, platform, streams, cue parsers, preload/transition strategies, translator, realtime)
- The plugin runtime (registration, lifecycle, dependency checks, translation merging)
- The event bus and the complete `BaseEventMap`
- The error hierarchy and retry policy
- DOM construction helpers

Anything NoMercy-specific (server auth, SignalR sync, watch-history writes) lives in layer 5.
The core and per-library packages stay generic, they know nothing about the NoMercy server API.

## Adapter ports

The core exposes adapter contracts that consumers swap without subclassing the player.
See the Adapter Ports section in the navigation for the full list.
The most commonly swapped ports are:

| Port                 | Default                                                                     | Why swap                                                      |
| -------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `platform`           | `browserPlatform`                                                           | Capacitor, Tauri, Electron native APIs                        |
| `storage`            | `LocalStorageBackend`                                                       | IndexedDB for larger values; remote API for cross-device sync |
| `streams`            | `hls` + `native`                                                            | Custom stream protocol, DASH, low-latency HLS                 |
| `cueParsers`         | VTT + LRC + sprite-VTT                                                      | TTML, SRT, ASS, proprietary formats                           |
| `preloadStrategy`    | `DefaultPreloadStrategy`                                                    | Different timing heuristics                                   |
| `transitionStrategy` | `GaplessTransitionStrategy` (video) / `CrossfadeTransitionStrategy` (music) | Custom fades or creative transitions                          |
| `translator`         | `DefaultTranslator`                                                         | i18next, FormatJS, any ICU-capable engine                     |
| `websocketFactory`   | `nativeWebSocketAdapter`                                                    | SignalR, Socket.IO                                            |

## Mixin composition

The player prototype is assembled at class definition time from 15+ mixins via `composeMixins`.
Each mixin owns one surface:

```ts
composeMixins(PlayerClass, [
  lifecycleMethods, // setup, dispose, ready, phase
  transportMethods, // play, pause, stop, next, previous, rewind, forward, restart
  timeMethods, // currentTime, duration, buffered, timeData, playbackRate
  volumeMethods, // volume, mute, unmute, toggleMute, volumeUp, volumeDown
  queueMethods, // queue, queueAppend, current, backlog, ...
  loadingMethods, // load, loadQueue
  mediaTracksMethods, // subtitles, audioTracks, qualityLevels, chapters
  // ...and more
]);
```

This means a fix in `volumeMethods` lands once and applies identically to both the music and video player.
